# `/yultopia:cc` 설계 — Claude가 작업하고 Codex가 PM을 맡는 자동 협업

작성일: 2026-10-17 (같은 날 사용자 결정으로 개정: 마일스톤 단위 호출, 상태 위치, 시작 조건, 중단 처리, 검증, 14일 자동 정리와 SessionStart 정리)
대상 저장소: `jeonyul00/yultopia` (Claude Code 플러그인 마켓플레이스, 플러그인 본체는 `plugins/yultopia/`)

---

## 1. 왜 만드는가

사용자는 지금까지 터미널 두 개(Claude Code, Codex)를 띄워 놓고 이렇게 일했다.

- Codex: PM. 지시·검수·리뷰·승인/반려·책임
- Claude: 구현자. 실제 작업
- 둘 사이의 지시문과 작업 보고를 **사용자가 직접 복붙**

`/yultopia:collab`(기존 스킬)은 이 수동 방식을 돕는다. 문제는 두 가지다.

1. 복붙이 불편하다.
2. 토큰을 많이 쓰는 느낌이다. (전문을 옮기고, 작은 작업마다 Codex를 부르고, 보고가 길다)

이번 기능은 **터미널 하나(Claude Code)에서 사용자는 Claude하고만 말하고, Claude↔Codex 주고받기는 자동으로** 하게 만든다. 역할은 기존 `/yultopia:collab`과 같다.

- Codex: PM, 지시자, 검수자
- Claude: 구현자
- **사용자의 지시가 항상 최우선**

사용자가 중간에 끼어드는 이유는 두 가지뿐이다.

- 잘 돌고 있는지 지켜보려고 (렉인지 일하는 중인지 모름)
- 기획이나 코딩 방향이 이상하게 흐를 때 바로잡으려고

시작은 Codex가 아니라 **Claude와의 대화**다. 사용자는 거칠고 대충 말한다. 빠진 정보는 Claude가 인터뷰해서 채운다.

참고 자료: [openai/codex-plugin-cc](https://github.com/openai/codex-plugin-cc). 구조와 프롬프트 작성 방식만 참고하고 코드는 가져오지 않는다. 이 플러그인에는 Codex를 PM으로 두는 흐름이 없다(Codex는 리뷰어 또는 작업자일 뿐).

## 2. 목표 / 비목표 / 실패 조건

### 목표

- `/yultopia:cc <자유 텍스트>` 로 시작한다.
- Claude가 인터뷰해서 **요구사항 정리본**을 만들고 사용자 승인을 받는다.
- 승인 뒤에는 자동으로 돈다. Codex는 **마일스톤 단위로만** 부른다.
- 사용자는 화면에서 진행을 볼 수 있고, 필요할 때 끊고 방향을 바꿀 수 있다.
- 기존 수동 `/yultopia:collab` 보다 토큰을 덜 쓴다.
- 작업 흔적이 쌓이지 않는다. 저장소당 진행 중 작업 기록은 최대 하나다.

### 비목표 (이번에 안 만든다)

- Codex가 코드를 고치는 기능 (codex-plugin-cc 의 `rescue` 같은 위임)
- codex-plugin-cc 기능 전체 복제 (`review`, `adversarial-review`, `transfer`, `status`/`result`/`cancel` 별도 명령)
- 응답이 끝날 때마다 도는 Stop 훅 자동 검수 (얼마 전 일부러 삭제한 기능이다). Stop 훅은 추가하지 않는다. 훅은 두 가지만 더한다: 기존 SessionStart 훅에 오래된 기록 정리(5-4), 그리고 **UserPromptSubmit 훅에 고아 Codex 확인**(6장. 확인만 하고 프로세스를 죽이지 않으며, Codex를 부르지 않는다. 현재 저장소에 active가 없으면 바로 끝난다). UserPromptSubmit 훅은 사용자가 승인했다. 조건: Codex를 호출하지 않는다 / 네트워크를 쓰지 않는다 / 활성 `/cc` 작업이 없으면 아무것도 출력하지 않고 즉시 끝난다 / 활성 작업이 있을 때만 고아 확인이 필요하다는 정보를 Claude에게 전달한다 / 프로세스를 직접 죽이지 않는다 / 오류가 나도 사용자 메시지를 막지 않는다 / 최대한 빨리 끝난다 / 예전 codex-review 훅처럼 메시지마다 긴 작업을 시작하지 않는다.
- cron, launchd, 상시 백그라운드 프로세스
- 자동 커밋·푸시
- 기존 `/yultopia:collab` 변경 (이름·내용 그대로 둔다)
- 커밋되지 않은 변경이 있는 상태에서의 시작 (첫 버전에서는 지원하지 않는다)
- 작업 이력 보관 (history 폴더를 만들지 않는다)

### 실패 조건 (돌아가더라도 이러면 실패)

- 사용자가 10분 넘게 아무 소식도 못 듣는다.
- 파일 하나·사소한 단계마다 Codex를 부른다.
- Claude와 Codex가 끝없이 주고받으며 토큰만 쓴다.
- Codex 이벤트 로그 전문이 Claude 컨텍스트(Bash 출력, 응답)에 들어온다.
- Codex 지시가 사용자가 인터뷰에서 말한 것과 다른데 Claude가 묻지 않고 따른다.
- Codex가 파일을 고쳐서 Claude 작업과 꼬인다.
- 사용자가 중단했는데 Codex 프로세스가 뒤에서 계속 돈다.
- 중단된 작업 기록이 여러 개 쌓인다.
- 엉뚱한 프로세스나 엉뚱한 경로를 지운다.

## 3. 사용자 흐름

### 3-1. 시작

```
/yultopia:cc 로그인 할 때 비번 5번 틀리면 잠그는 거 넣고 싶은데 어쩌구 저쩌구
```

- 인자 = 사용자의 생각·요구 원문. 그대로 인터뷰 출발점으로 쓴다.
- 인자가 없으면 "무엇을 할까요?" 한 줄로 묻고 시작한다.

시작할 때 이 순서로 확인한다.

1. **git 저장소인지**: 아니면 안내하고 중단한다. (Codex가 `git diff`로 검수하고, 상태도 git 디렉터리에 저장하기 때문)
2. **Codex CLI 설치·로그인**: 안 돼 있으면 안내하고 중단한다.
3. **남아 있는 active 작업 정리** (5장 참고):
   - 오래된 기록 자동 삭제 규칙(5-4)을 적용한다. 지웠으면 "오래된 `/cc` 중단 기록을 정리했습니다" 한 줄 알린다.
   - 살아 있는 고아 Codex 프로세스가 있으면 사용자에게 알리고 종료한다(6장). (이 단계는 사용자가 있는 `/cc` 실행 때만 한다. SessionStart 훅은 프로세스를 죽이지 않는다)
   - active가 남아 있으면 **이어 하기 / 버리기**를 묻는다.
     - 이어 하기: 저장된 상태에서 재개한다. 이 경우 작업 트리에는 이전 `/cc` 작업의 변경이 있으므로 4번 검사를 하지 않고, 변경 파일 요약만 보여준다.
     - 버리기: active를 삭제한 뒤 새 작업으로 간다. **코드 변경은 건드리지 않는다.** 따라서 작업 트리가 깨끗하지 않으면 4번 검사에서 중단된다.
4. **작업 트리가 깨끗한지** (새 작업일 때만):
   - 커밋되지 않은 변경이나 untracked 파일(무시 목록에 없는 것)이 있으면:
     - 변경된 파일을 짧게 보여준다.
     - 기존 변경과 `/cc` 변경을 구분할 수 없어서 시작할 수 없다고 설명한다.
     - **그대로 진행할지 묻지 않고 중단한다.**
   - `/cc` 자체 상태 파일은 git 디렉터리 안(작업 트리 밖)에 있으므로 이 검사에 걸리지 않는다.

### 3-2. 인터뷰

- 한 번에 질문 하나, 쉬운 말로 묻는다. 사용자가 욕을 하거나 대충 말해도 핵심만 뽑는다.
- 코드·문서로 알 수 있는 건 묻지 않고 직접 확인한다. (`AGENTS.md`, `CLAUDE.md`, `## Yultopia 중점 점검 항목` 절, 관련 코드)
- 정리본에 채울 항목:
  - 목표: 무엇을, 왜
  - 완료 기준: 어떻게 되면 끝인가
  - 범위: 할 것 / 안 할 것
  - 사용자가 이미 정한 방향 (기술 선택, 방식 등)
  - 제약·금지
  - **미리 허락한 위험 작업**: 이 작업에 필요한 위험 작업(DB 쓰기·스키마 변경, 파일·데이터 삭제, 보안·인증·개인정보, 외부 API 계약 변경, 의존성 추가, 배포)을 구체적으로 적는다. 예: "users 테이블에 failed_count, locked_until 컬럼 추가". 해당 작업이 보이면 인터뷰에서 꼭 짚어 묻는다.
  - 검증 방법 (실제 존재하는 테스트·빌드·린트 명령)
- 다 모이면 정리본을 짧게 보여주고 "이대로 시작할까요?"를 묻는다. 사용자가 고치면 반영한다. 승인("ㅇㅇ", "시작" 등)이 나오면 정리본을 active에 저장하고 첫 Codex 호출로 간다.

### 3-3. 마일스톤 루프

Codex는 **마일스톤 단위로만** 부른다. 파일 하나 수정할 때마다, 또는 사소한 단계마다 부르지 않는다.

**첫 Codex 호출**: 정리본을 주고 다음을 한꺼번에 받는다.

- 전체 작업 계획
- 큰 마일스톤 목록
- 각 마일스톤의 완료 기준
- 첫 번째 마일스톤의 구체적인 작업 지시

Claude는 계획 요약과 마일스톤 목록을 화면에 짧게 보여주고, **사용자 승인 없이 바로 첫 마일스톤을 시작한다** (요구사항 정리본을 이미 사용자가 승인했기 때문). 단, 계획이 승인된 정리본의 목표나 범위를 바꾸면 시작하지 말고 사용자에게 묻는다. (사용자 결정)

**마일스톤 하나의 흐름**:

1. Claude가 그 마일스톤 전체를 작업한다. 중간에 Codex를 부르지 않는다.
2. Claude가 검증 명령(지시된 것, 없으면 정리본의 검증 방법)을 실행한다. 출력 원문은 잘라내거나 고치지 않고 active 안에 파일로 저장한다.
3. Claude가 짧은 보고와 함께 Codex를 부른다(같은 Codex 대화 이어서). 보고: 바뀐 파일 목록, 핵심 변경 한두 줄, 검증 결과 한 줄 + 출력 원문 파일 경로, 못 한 것·리스크, 반대 의견(있으면). **diff 본문은 넣지 않는다.**
4. Codex가 실제 diff와 파일을 직접 보고 그 마일스톤을 검수한다.
   - 승인 → 다음 마일스톤의 구체적인 지시를 준다.
   - 반려 → 그 마일스톤만 보완할 내용을 준다. Claude가 보완하고 다시 3으로.
5. 모든 마일스톤이 끝나면 **최종 검수**를 받는다: 전체 변경이 정리본의 목표·완료 기준을 모두 채웠는지.

정상 작업의 Codex 호출 수 = 1(계획) + 마일스톤 수(각 검수, 마지막 것은 최종 검수 포함) + 반려 횟수 + 사용자 확인 질문 수.

**Codex 지시를 받았을 때 Claude의 판단** (정리본에 없는 것만 멈춘다, 사용자 결정):

- 정리본의 「미리 허락한 위험 작업」에 있는 작업 → 멈추지 않고 진행한다.
- 거기에 없는 위험 작업 → **멈추고 사용자에게 묻는다.**
- 정리본의 목표·범위·사용자가 정한 방향을 바꾸는 지시 → **멈추고 묻는다.**
- 범위 안의 작은 단계(테스트 추가, 작업에 필요한 작은 정리 등) → 멈추지 않는다.
- 사용자가 중간에 승인한 위험 작업은 정리본에 추가해서 다음부터는 묻지 않는다.
- Claude가 지시가 기술적으로 틀렸다고 판단하면, 그 부분은 구현하지 않고 보고에 반대 이유를 적어 Codex에게 보낸다. Codex가 같은 지시를 다시 고집하면 사용자에게 묻는다.
- Codex가 `ask_user`를 내면 Codex의 질문임을 밝히고 사용자에게 그대로 묻고, 답을 Codex에게 전달한다.

### 3-4. 멈춤 조건

- 같은 마일스톤에서 **연속 반려 3회** → 멈추고, 무엇이 반복해서 반려되는지 요약해 사용자에게 어떻게 할지 묻는다.
- **전체 Codex 호출 20회** 도달 → 멈추고 묻는다. 이것은 안전장치다. 정상 작업에서는 위의 마일스톤 단위 호출만 일어난다.
- Codex 호출 한 번의 **실행 시간 상한은 20분**이다. (사용자 결정)
  - 20분을 다 쓴 시간 초과 → **자동 재시도하지 않는다.** Codex 프로세스 그룹을 종료하고 사용자에게 보고한다.
  - 실행 직후 생긴 명확한 기술 오류(프로세스가 바로 비정상 종료, 실행 파일·인증·네트워크 오류 등) → 1회 재시도. 또 실패하면 멈추고 보고한다.
  - 잘못된 JSON → 같은 Codex 대화에 형식만 고쳐 다시 달라고 1회 요청. 또 실패하면 멈추고 보고한다.
  - 어느 경우든 active는 남긴다.
- 사용자가 끊으면(Esc 등) → 진행 중인 Codex 프로세스를 종료한다(6장). 사용자가 방향을 바꾸면 그 내용을 정리본에 반영하고, Codex에게 "사용자 지시"로 전달한 뒤 이어 간다. **사용자의 말이 Codex 지시보다 항상 우선이다.**

### 3-5. 완료와 정리

1. Codex가 `done`을 내도 **바로 지우지 않는다.**
2. Claude가 최종 결과를 사용자에게 보여준다: 마일스톤별 결과, 바뀐 파일, 검증 결과, Codex가 남긴 지적(있으면), Codex 토큰 사용량.
3. 사용자에게 완료 여부와 커밋 여부를 묻는다. 커밋은 사용자가 하라고 할 때만 한다. 푸시는 하지 않는다(따로 지시하면 예외).
4. 사용자가 **완료라고 확인하면** active 폴더를 삭제한다.
5. 사용자가 **추가 수정을 요구하면** 같은 active 작업을 이어간다. 그 요구는 Codex에게 사용자 지시로 전달해 새 마일스톤으로 처리한다.

### 3-6. 진행 보고

- 단계가 바뀔 때마다 한 줄. 예:
  - `[cc] Codex 계획: 마일스톤 3개 (1 실패 횟수 저장 / 2 잠금 처리 / 3 테스트)`
  - `[cc 1/3] Claude 작업 중`
  - `[cc 1/3] Codex 검수 중`
  - `[cc 1/3] Codex 반려 (1/3): 잠금 해제 시간이 없음`
  - `[cc 2/3] Codex 승인 → 다음: 잠금 처리`
- 같은 단계가 10분 넘게 이어지면 **10분마다 짧은 생존 보고**: 경과 시간, 지금 하는 일, 살아 있는지(Codex 프로세스 생존 여부와 마지막 활동 시각).
- 구현 방법: Claude는 도구 호출이 끝나야 말할 수 있다. Codex는 백그라운드로 띄우고, Claude는 "최대 약 9분 기다렸다 한 줄 상태나 최종 JSON을 돌려주는" 대기 명령을 반복 호출하면서 그 사이에 보고한다. (Bash 도구 1회 최대 10분 제한 안쪽)
- Claude 자신의 구현이 길어질 때도 도구 호출 사이사이에 대략 10분마다 한 줄 보고한다.

## 4. Codex 호출

### 4-1. 모델과 추론 강도

- Codex 모델과 추론 강도는 **사용자의 기존 Codex 설정(`~/.codex/config.toml` 등)을 그대로** 쓴다.
- 토큰을 줄인다는 이유로 모델이나 추론 강도를 낮추거나 덮어쓰지 않는다.
- `-m`, `model_reasoning_effort` 같은 옵션을 지정하지 않는다. 실제 Codex smoke test(8장)도 같다.
- 별도로 강제할 수 있는 설정은 **읽기 전용 보장을 위한 sandbox 설정뿐**이다.
- 사용자의 현재 설정은 추론 강도가 높아 한 번 호출에 몇 분 걸릴 수 있다. 10분 생존 보고로 커버한다.

### 4-2. 호출 방식

- 첫 호출: `codex exec`. 이후: `codex exec resume <세션ID>`. 같은 Codex 대화를 이어 쓰므로 Codex가 앞 내용을 기억하고, 정리본을 다시 보내지 않는다.
- **읽기 전용 강제**: `exec` 는 `-s read-only`. `resume` 에는 `--sandbox` 옵션이 없으므로 `-c sandbox_mode="read-only"` 같은 설정 덮어쓰기로 강제한다. **이 방법이 실제로 먹히는지 검증한다(8장).** 안 먹히면 다른 방법을 찾고, 못 찾으면 사용자에게 알린다. Codex 쓰기 차단은 필수 요건이다.
- 읽기 전용의 목적은 **Codex가 코드를 고쳐 Claude 작업과 꼬이는 것을 막는 것**이다. 사용자 Codex 설정에 켜져 있는 MCP 서버(playwright, chrome-devtools)와 플러그인은 끄지 않는다(설정 그대로 원칙). 이들은 샌드박스 밖에서 돌지만 프로젝트 코드를 고치는 도구가 아니므로 허용하고, PM 프롬프트에서 "어떤 도구로도 프로젝트 파일을 만들거나 고치지 말 것"을 명시한다.
- 출력: `--output-schema <스키마>` + `-o <파일>` 로 마지막 메시지(JSON)를 active 안 파일로 받는다.
- `--json` 이벤트 스트림은 **active 안 로그 파일에만** 저장한다. 세션 ID 추출, 마지막 활동 시각, 토큰 사용량 기록에 쓴다. 이벤트 이름·구조는 실제 출력으로 확인한다.
- stdin 은 반드시 닫는다(`</dev/null`). 안 닫으면 입력 대기로 무한정 멈춘다.
- `resume` 에는 작업 폴더 지정 옵션(`-C`)이 없으므로 저장소 루트에서 실행한다.
- 확인된 환경: codex-cli 0.163.0. `exec`, `exec resume`, `--json`, `-o`, `--output-schema`, `-s` 존재 확인함.

### 4-3. Claude 컨텍스트로 돌아오는 것

- 대기 명령은 **진행 상태 한 줄** 또는 **최종 JSON 결과**만 출력한다.
- JSONL 이벤트 로그 전문, Codex의 중간 메시지, 명령 실행 출력은 Bash 출력이나 Claude 응답에 넣지 않는다. 필요하면 파일 경로만 알려준다.

### 4-4. Codex 출력 형식 (JSON)

| 필드 | 설명 |
|---|---|
| `verdict` | `plan` (첫 호출) / `approve` (현재 마일스톤 승인 + 다음 지시) / `reject` (현재 마일스톤 보완) / `done` (최종 검수 통과) / `ask_user` |
| `summary` | 화면에 보여줄 한 줄 요약 (한국어) |
| `plan` | 전체 계획 요약 + 마일스톤 목록(번호, 이름, 완료 기준). `plan` 일 때 필수. `approve` 때 계획을 바꾸면 갱신본 |
| `milestone` | 지금 지시하는 마일스톤 번호 |
| `instruction` | 해당 마일스톤의 구체적 지시. 목표, 수정 범위, 지킬 것, 금지, 검증 명령, 완료 기준. `plan`/`approve`/`reject` 일 때 |
| `findings` | 반려·지적 목록. 항목마다 파일, 줄(가능하면), 내용, 근거. `reject` 일 때 필수, `done` 일 때 남은 사소한 지적 |
| `question` | 사용자에게 물을 것. `ask_user` 일 때 |

- Codex가 `approve` 에서 마일스톤 계획을 바꾸면 Claude는 바뀐 점을 한 줄 보고한다. 목표·범위가 바뀌면 3-3 규칙대로 멈추고 묻는다.
- 세부 필드명·필수 여부는 빌더가 정한다.

### 4-5. PM 역할 프롬프트에 들어갈 내용

- 역할: PM·지시자·검수자. **직접 구현 금지, 어떤 도구로도 프로젝트 파일 생성·수정 금지.** 사용자 지시가 최우선.
- 정리본 전문 (첫 호출에만)
- 진행 방식: 마일스톤 단위. 첫 응답에서 전체 계획·마일스톤·완료 기준·첫 마일스톤 지시를 한꺼번에. 마일스톤을 잘게 쪼개지 말 것.
- 검수 방식: Claude 보고를 믿지 말고 `git diff`·파일과 저장된 검증 출력 원문을 직접 확인. Codex는 테스트·빌드를 다시 돌리지 않는다(읽기 전용이라 캐시·결과 파일 쓰기에서 권한 오류가 난다). 권한 오류로 실패한 명령을 근거로 반려하지 말 것. 근거 없는 지적 금지, 추정은 추정이라고 표시. 정리본의 완료 기준을 모두 채웠을 때만 `done`.
- 프로젝트 규칙: Codex는 실행 위치의 `AGENTS.md` 를 스스로 읽는다. `## Yultopia 중점 점검 항목` 절이 있으면 그것을 검수 우선순위로 삼으라고 명시한다.
- 언어: 한국어.
- 문체: codex-plugin-cc 의 `skills/gpt-5-4-prompting` 처럼 XML 블록(`<task>`, `<structured_output_contract>`, `<grounding_rules>` 등)으로 짧고 구조적으로 쓴다.

## 5. 상태 저장과 찌꺼기 정리

### 5-1. 위치

- `<git-dir>/yultopia-cc/active/`
- `<git-dir>` 는 `git rev-parse --git-dir` 로 구한다(절대 경로로 정규화. `--absolute-git-dir` 사용 가능). 작업 트리 밖이므로 `git status`·`git diff` 에 섞이지 않고, 프로젝트 `.gitignore` 를 건드릴 필요가 없다.
- 기존 설계의 `<프로젝트>/.claude/cc/` 방식은 쓰지 않는다.

### 5-2. 내용

active 안에 저장한다.

- 요구사항 정리본
- Codex 세션 ID
- 현재 마일스톤, 마일스톤 계획
- 전체 호출 횟수, 마일스톤별 연속 반려 횟수
- 실행 중 Codex의 PID, 프로세스 그룹 ID, 프로세스 시작 시각 (실행 중인 호출이 없으면 비어 있음을 명시적으로 기록)
- 마지막 활동 시각 `last_activity_at` (상태 파일 안의 값. 상태가 바뀌거나 Codex 이벤트가 올 때마다 갱신)
- Codex JSONL 이벤트 로그, 호출별 JSON 결과
- Claude의 검증 출력 원문
- Codex 토큰 사용량 누계

### 5-3. 규칙

- 저장소마다 active 작업은 **최대 하나**.
- 작업 이력을 쌓는 history 폴더는 만들지 않는다.
- Codex가 `done`을 내도 즉시 삭제하지 않는다. 사용자가 완료라고 확인하면 삭제한다(3-5).
- 사용자가 추가 수정을 요구하면 같은 active를 이어간다.
- 중단, 오류, Claude 세션 종료 시에는 재개를 위해 active를 남긴다.
- 다음 `/yultopia:cc` 실행 때 active가 있으면 이어 하기 / 버리기를 묻는다. 버리기면 삭제 후 새 작업.
- 오래된 active는 5-4 규칙으로 자동 삭제한다.
- **삭제 안전 규칙**: 삭제는 확인된 `<git-dir>/yultopia-cc/active` 정확한 경로에만 한다. `active` 나 `yultopia-cc` 가 심볼릭 링크이거나, 경로가 `<git-dir>` 아래가 아니거나, 그 밖에 비정상이면 삭제하지 말고 중단한다. (SessionStart 훅에서는 "중단" 대신 경고만 하고 넘어간다)

이 방식이면 정상 완료 기록은 바로 없어지고, 중단된 작업도 하나만 남는다.

### 5-4. 오래된 기록 자동 삭제 (14일)

- **언제**: `/yultopia:cc` 실행 때, 그리고 Yultopia의 **SessionStart 훅**(기존 인수인계서 주입 훅과 같은 시점)에서. 별도 cron, launchd, 상시 백그라운드 프로세스는 만들지 않는다.
- **대상**: 현재 저장소의 `<git-dir>/yultopia-cc/active` 하나. (SessionStart 훅은 세션이 시작된 프로젝트의 저장소만 본다. 다른 저장소의 기록은 그 저장소에서 세션이 시작되거나 `/cc` 가 실행될 때 정리된다)
- **만료 판단**: 파일 mtime이 아니라 상태 파일의 `last_activity_at` 값으로 한다. 14일이 넘었을 때만 만료로 본다.
- **삭제 조건** (모두 만족할 때만 삭제):
  1. `last_activity_at` 이 14일을 넘었다.
  2. 그 작업에 기록된 Codex 프로세스가 실제로 살아 있지 않다. 다음 중 하나로 **확실히** 판단될 때만 "살아 있지 않음"으로 본다.
     - 실행 중인 호출이 없다고 상태에 명시적으로 기록돼 있다.
     - 기록된 PID가 존재하지 않는다.
     - 기록된 PID는 있지만 시작 시각·명령 이름이 저장값과 달라 다른 프로세스가 재사용한 것이 확실하다.
  3. 삭제 안전 규칙(5-3)을 통과한다.
- **삭제하지 않고 경고만 하는 경우**:
  - 기록된 Codex 프로세스가 살아 있다.
  - PID 검증이 불확실하다 (상태 파일을 읽을 수 없음, `last_activity_at` 이 없거나 형식이 틀림, 프로세스 정보를 조회할 수 없음 등).
  - 경로가 비정상이다.
- **알림**: 삭제했으면 "오래된 `/cc` 중단 기록을 정리했습니다" 한 줄. 경고는 무엇 때문에 지우지 않았는지 한 줄.
- **SessionStart 훅 제약**: 빨리 끝나야 하고(Codex를 부르지 않는다, 프로세스를 죽이지 않는다), 어떤 경우에도 세션 시작을 깨뜨리지 않는다(항상 정상 종료). 알림은 사용자에게 보이는 방식으로 낸다. 기존 인수인계서 주입 기능과 함께 동작해야 한다.

## 6. 중단 처리 (프로세스)

사용자가 Esc로 중단했을 때 대기용 셸만 죽고 Codex가 뒤에서 계속 돌면 안 된다. 셸 방식으로 구현하되 다음을 지킨다.

- Codex 프로세스를 **별도 프로세스 그룹**으로 실행한다. (macOS에는 `setsid` 명령이 기본으로 없으므로 다른 방법이 필요하다. 빌더가 확인)
- PID와 가능하면 프로세스 그룹 ID, 프로세스 시작 시각을 active 상태에 저장한다.
- 대기 스크립트가 **SIGINT 또는 SIGTERM**을 받으면 해당 Codex 프로세스 그룹도 종료한다.
- 종료 전에 **PID 검증**: 저장된 PID가 아직 살아 있고, 시작 시각과 명령 이름(codex)이 저장값과 일치할 때만 죽인다. 이미 끝났거나 다른 프로세스가 재사용한 PID는 건드리지 않는다.
- Codex 호출마다 **실행 시간 상한 20분**. 넘으면 프로세스 그룹을 종료하고 재시도 없이 보고한다(3-4). 대기 명령이 죽어 있어도 상한이 지켜지도록, 상한 감시는 Codex를 띄운 쪽(대기 명령이 아닌 쪽)이 맡는다.
- **받아들인 제한** (사용자 결정): Esc를 누른 시점에 대기 명령이 돌고 있지 않거나 강제 종료(SIGKILL)로 끊기면 Codex가 즉시 종료되지 않을 수 있다. 대신 아래 세 가지를 **반드시 구현하고 테스트한다.**
  1. 실행 시간 상한 20분 (위)
  2. **다음 사용자 메시지에서 고아 프로세스 확인**: Codex가 살아 있는데 그것을 기다리는 대기 명령이 일정 시간(예: 60초) 넘게 없으면 고아로 본다. 사용자가 다음 메시지를 보내면 UserPromptSubmit 훅이 이를 감지해 Claude에게 알리고(훅은 죽이지 않는다), Claude는 사용자 말에 맞춰 종료하거나 다시 기다린다. 대기 명령의 PID와 마지막 대기 종료 시각도 상태에 기록한다.
  3. **다음 `/cc` 실행 시 확인**: active 상태와 실제 프로세스 생존 여부를 확인한다. 살아 있는 고아 Codex 프로세스가 있으면 사용자에게 알리고 종료한 뒤 재개 여부를 판단한다.

## 8. 검증 (구현 완료 조건)

### 8-1. 가짜 Codex 자동 테스트

실제 `codex` 대신 동작을 흉내 내는 가짜 실행 파일로 스크립트를 검증한다. (codex-plugin-cc 의 `tests/fake-codex-fixture.mjs` 참고) 오류, 잘못된 JSON, 시간 초과, 상태 복원은 **모두 여기서** 확인한다. 다음을 자동 테스트로 확인한다.

- 첫 세션 생성과 세션 ID 저장
- 같은 세션으로 재개 호출
- JSON 결과 수신과 스키마 검사
- 잘못된 JSON → 형식 재요청 1회, 또 실패하면 중단
- 실행 직후 기술 오류 → 1회 재시도, 또 실패하면 중단
- 시간 상한 초과 → 프로세스 그룹 종료, 재시도 없이 중단 보고 (대기 명령이 없어도 상한이 지켜지는지)
- 다음 사용자 메시지에서 고아 프로세스 감지 (대기 명령 없음 + Codex 살아 있음)
- 대기 스크립트가 SIGINT/SIGTERM을 받으면 Codex 프로세스 그룹까지 종료
- 끝난 PID·재사용된 PID를 죽이지 않음
- 고아 프로세스 감지와 종료
- 재시작(새 셸)에서 active 상태로 재개
- 정상 완료 확인 후 active 삭제
- `last_activity_at` 이 14일 넘고 Codex가 확실히 죽어 있으면 자동 삭제 (`/cc` 실행 때와 SessionStart 훅 양쪽)
- 14일 넘었어도 Codex가 살아 있거나 PID 검증이 불확실하면 삭제하지 않고 경고
- 파일 mtime은 오래됐지만 `last_activity_at` 은 최근이면 삭제하지 않음
- SessionStart 훅이 어떤 상태에서도 정상 종료하고, 인수인계서 주입과 함께 동작
- active가 여러 개 쌓이지 않음 (새 작업 시작 시 기존 active 처리)
- 심볼릭 링크·비정상 경로면 삭제하지 않고 중단
- 작업 트리가 깨끗하지 않으면 새 작업 시작 거부
- 대기 명령 출력이 한 줄 상태 또는 최종 JSON뿐인지 (로그 전문이 섞이지 않는지)

## 9. 결정 기록

### 사용자가 정한 것

- 명령 이름 `/yultopia:cc`, 인자로 자유 텍스트
- 시작은 Claude와의 대화, 부족한 정보는 Claude가 인터뷰. 정리본 승인 후 시작
- 역할: Codex는 PM·지시자·검수자, Claude는 구현자, 사용자 지시가 항상 최우선
- Codex는 마일스톤 단위로만 호출. 첫 호출에서 전체 계획·마일스톤·완료 기준·첫 지시를 한꺼번에
- 연속 반려 3회 제한 유지, 전체 호출 상한은 안전장치로 유지
- 승인 후 자동 진행, 사용자는 필요할 때만 끊는다
- 단계 바뀔 때 한 줄 + 같은 단계 10분 넘으면 생존 보고
- Codex는 읽기 전용, 코드는 Claude만 고친다
- 위험 작업은 정리본에 미리 적고 승인한 것이면 멈추지 않는다. 정리본에 없는 위험 작업이나 사용자 요구와 충돌하는 지시만 멈추고 묻는다
- Codex 모델·추론 강도는 사용자 설정 그대로. 덮어쓰지 않는다. sandbox 설정만 강제
- JSONL 로그는 파일에만. Claude에는 한 줄 상태와 최종 JSON만
- 새 작업은 작업 트리가 깨끗할 때만 시작. 아니면 묻지 않고 중단
- 상태는 `<git-dir>/yultopia-cc/active/`. 저장소당 하나, history 없음
- `done` 후 사용자 확인 시 삭제, 추가 수정이면 이어감, 중단·오류 시 보존, 다음 실행 때 이어 하기/버리기, 삭제 경로 엄격 검증
- 자동 삭제는 14일 기준, `last_activity_at` 으로 판단(mtime 아님), Codex가 확실히 죽어 있을 때만. 살아 있거나 불확실하면 경고만. `/cc` 실행 때와 SessionStart 훅에서 수행. cron·launchd·상시 프로세스 없음. 삭제 시 한 줄 알림
- Codex 별도 프로세스 그룹 실행, PID 검증, 신호 받으면 그룹 종료, 다음 실행 때 고아 확인
- 셸 스크립트 + `codex exec`/`codex exec resume` 방식. 가짜 Codex 자동 테스트 + 실제 smoke test 최대 3회(세션 시작, 같은 세션 재개, 중단 확인). Claude 재시작 후 이어 하기는 구현 후 사용자가 직접 1회 확인
- Codex 계획은 요약을 보여주고 승인 없이 바로 첫 마일스톤 시작. 단 정리본의 목표·범위를 바꾸면 묻는다
- Esc 시점에 따라 Codex가 즉시 안 꺼질 수 있는 제한은 받아들인다. 대신 실행 시간 상한, 다음 사용자 메시지에서 고아 확인, 다음 `/cc` 실행 시 확인을 반드시 구현·테스트
- Codex 호출당 실행 시간 상한 20분. 시간 초과는 자동 재시도 없이 보고, 실행 직후 명확한 기술 오류만 1회 재시도
- 자동 커밋·푸시 안 함. 완료 후 커밋 여부를 묻는다
- 기존 `/yultopia:collab` 은 이름·내용 그대로 유지

### Claude가 정한 것 (사용자가 바꿀 수 있음)

- Codex 판정 5종 (`plan`/`approve`/`reject`/`done`/`ask_user`)과 출력 필드
- 마지막 마일스톤 검수와 최종 검수를 한 번의 호출로 처리
- Codex가 `approve` 때 마일스톤 계획을 바꿀 수 있음. 한 줄 보고, 목표·범위가 바뀌면 멈춤
- 전체 호출 상한 20회
- 잘못된 JSON은 같은 대화에 형식 재요청 1회
- 고아 판정: Codex 살아 있음 + 대기 명령이 60초 넘게 없음. 대기 명령 PID와 마지막 대기 종료 시각 기록
- 시간 상한 감시는 Codex를 띄운 쪽이 맡음 (대기 명령이 죽어도 상한 유지)
- Claude가 지시에 반대할 때: 보고에 이유를 적고, Codex가 고집하면 사용자에게 묻는다
- 이어 하기는 작업 트리 검사를 건너뛰고 변경 요약만 보여줌
- 버리기는 상태만 지우고 코드 변경은 건드리지 않음 (그래서 작업 트리가 지저분하면 새 작업은 시작 조건에 걸림)
- PID 검증에 시작 시각과 명령 이름 사용
- 중단 후 같은 세션의 다음 메시지에서 Claude가 실행 중인 Codex를 확인·정리
- 추가 수정 요구는 새 마일스톤으로 Codex에 전달
- Codex의 MCP 서버·플러그인은 끄지 않고 프롬프트로 파일 수정 금지
- Codex는 테스트를 다시 돌리지 않고, 저장된 검증 출력 원문과 읽기 전용 확인으로 판단
- Codex 토큰 사용량은 기록해서 최종 보고에 보여주고, 출시 전 유료 비교 실험은 하지 않음
- Codex 대기는 백그라운드 + 최대 약 9분 대기 명령 반복
- 버전 2.1.0
