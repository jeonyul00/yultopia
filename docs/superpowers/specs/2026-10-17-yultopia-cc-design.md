작성일: 2026-10-17 (같은 날 사용자 결정으로 개정: 마일스톤 단위 호출, 상태 위치, 시작 조건, 중단 처리, 검증, 14일 자동 정리와 SessionStart 정리)
개정: 2026-10-18 — Codex가 테스트를 직접 돌린다 (10장 "2026-10-18 변경", R31/R32), 같은 날 보안 수정 (10장 끝 "2026-10-18 보안 수정", R33/R34). 아래 4장·8장·9장의 읽기 전용 설명은 그 변경으로 대체된다 (기록으로 남겨 둔다).
대상 저장소: `jeonyul00/yultopia` (Claude Code 플러그인 마켓플레이스, 플러그인 본체는 `plugins/yultopia/`)

## 1. 왜 만드는가

사용자는 지금까지 터미널 두 개(Claude Code, Codex)를 띄워 놓고 이렇게 일했다.

- Codex: PM. 지시·검수·리뷰·승인/반려·책임
- Claude: 구현자. 실제 작업
- 둘 사이의 지시문과 작업 보고를 **사용자가 직접 복붙**

`/yultopia:collab`(기존 스킬)은 이 수동 방식을 돕는다. 문제는 두 가지다.

1. 복붙이 불편하다.
2. 토큰을 많이 쓰는 느낌이다. (전문을 옮기고, 작은 작업마다 Codex를 부르고, 보고가 길다)

이번 기능은 **터미널 하나(Claude Code)에서 사용자는 Claude하고만 말하고, Claude↔Codex 주고받기는 자동으로** 하게 만든다. 역할은 기존 `/yultopia:collab`과 같다.

- Codex: PM, 지시자, 검수자
- Claude: 구현자
- **사용자의 지시가 항상 최우선**

사용자가 중간에 끼어드는 이유는 두 가지뿐이다.

- 잘 돌고 있는지 지켜보려고 (렉인지 일하는 중인지 모름)
- 기획이나 코딩 방향이 이상하게 흐를 때 바로잡으려고

시작은 Codex가 아니라 **Claude와의 대화**다. 사용자는 거칠고 대충 말한다. 빠진 정보는 Claude가 인터뷰해서 채운다.

참고 자료: [openai/codex-plugin-cc](https://github.com/openai/codex-plugin-cc). 구조와 프롬프트 작성 방식만 참고하고 코드는 가져오지 않는다. 이 플러그인에는 Codex를 PM으로 두는 흐름이 없다(Codex는 리뷰어 또는 작업자일 뿐).

## 2. 목표 / 비목표 / 실패 조건

### 목표

- `/yultopia:cc <자유 텍스트>` 로 시작한다.
- Claude가 인터뷰해서 **요구사항 정리본**을 만들고 사용자 승인을 받는다.
- 승인 뒤에는 자동으로 돈다. Codex는 **마일스톤 단위로만** 부른다.
- 사용자는 화면에서 진행을 볼 수 있고, 필요할 때 끊고 방향을 바꿀 수 있다.
- 기존 수동 `/yultopia:collab` 보다 토큰을 덜 쓴다.
- 작업 흔적이 쌓이지 않는다. 저장소당 진행 중 작업 기록은 최대 하나다.

### 비목표 (이번에 안 만든다)

- Codex가 코드를 고치는 기능 (codex-plugin-cc 의 `rescue` 같은 위임)
- codex-plugin-cc 기능 전체 복제 (`review`, `adversarial-review`, `transfer`, `status`/`result`/`cancel` 별도 명령)
- 응답이 끝날 때마다 도는 Stop 훅 자동 검수 (얼마 전 일부러 삭제한 기능이다). Stop 훅은 추가하지 않는다. 훅은 두 가지만 더한다: 기존 SessionStart 훅에 오래된 기록 정리(5-4), 그리고 **UserPromptSubmit 훅에 고아 Codex 확인**(6장. 확인만 하고 프로세스를 죽이지 않으며, Codex를 부르지 않는다. 현재 저장소에 active가 없으면 바로 끝난다). UserPromptSubmit 훅은 사용자가 승인했다. 조건: Codex를 호출하지 않는다 / 네트워크를 쓰지 않는다 / 활성 `/cc` 작업이 없으면 아무것도 출력하지 않고 즉시 끝난다 / 활성 작업이 있을 때만 고아 확인이 필요하다는 정보를 Claude에게 전달한다 / 프로세스를 직접 죽이지 않는다 / 오류가 나도 사용자 메시지를 막지 않는다 / 최대한 빨리 끝난다 / 예전 codex-review 훅처럼 메시지마다 긴 작업을 시작하지 않는다.
- cron, launchd, 상시 백그라운드 프로세스
- 자동 커밋·푸시
- 기존 `/yultopia:collab` 변경 (이름·내용 그대로 둔다)
- 커밋되지 않은 변경이 있는 상태에서의 시작 (첫 버전에서는 지원하지 않는다)
- 작업 이력 보관 (history 폴더를 만들지 않는다)

### 실패 조건 (돌아가더라도 이러면 실패)

- 사용자가 10분 넘게 아무 소식도 못 듣는다.
- 파일 하나·사소한 단계마다 Codex를 부른다.
- Claude와 Codex가 끝없이 주고받으며 토큰만 쓴다.
- Codex 이벤트 로그 전문이 Claude 컨텍스트(Bash 출력, 응답)에 들어온다.
- Codex 지시가 사용자가 인터뷰에서 말한 것과 다른데 Claude가 묻지 않고 따른다.
- Codex가 파일을 고쳐서 Claude 작업과 꼬인다.
- 사용자가 중단했는데 Codex 프로세스가 뒤에서 계속 돈다.
- 중단된 작업 기록이 여러 개 쌓인다.
- 엉뚱한 프로세스나 엉뚱한 경로를 지운다.

## 3. 사용자 흐름

### 3-1. 시작

```
/yultopia:cc 로그인 할 때 비번 5번 틀리면 잠그는 거 넣고 싶은데 어쩌구 저쩌구
```

- 인자 = 사용자의 생각·요구 원문. 그대로 인터뷰 출발점으로 쓴다.
- 인자가 없으면 "무엇을 할까요?" 한 줄로 묻고 시작한다.

시작할 때 이 순서로 확인한다.

1. **git 저장소인지**: 아니면 안내하고 중단한다. (Codex가 `git diff`로 검수하고, 상태도 git 디렉터리에 저장하기 때문)
2. **Codex CLI 설치·로그인**: 안 돼 있으면 안내하고 중단한다.
3. **남아 있는 active 작업 정리** (5장 참고):
   - 오래된 기록 자동 삭제 규칙(5-4)을 적용한다. 지웠으면 "오래된 `/cc` 중단 기록을 정리했습니다" 한 줄 알린다.
   - 살아 있는 고아 Codex 프로세스가 있으면 사용자에게 알리고 종료한다(6장). (이 단계는 사용자가 있는 `/cc` 실행 때만 한다. SessionStart 훅은 프로세스를 죽이지 않는다)
   - active가 남아 있으면 **이어 하기 / 버리기**를 묻는다.
     - 이어 하기: 저장된 상태에서 재개한다. 이 경우 작업 트리에는 이전 `/cc` 작업의 변경이 있으므로 4번 검사를 하지 않고, 변경 파일 요약만 보여준다.
     - 버리기: active를 삭제한 뒤 새 작업으로 간다. **코드 변경은 건드리지 않는다.** 따라서 작업 트리가 깨끗하지 않으면 4번 검사에서 중단된다.
4. **작업 트리가 깨끗한지** (새 작업일 때만):
   - 커밋되지 않은 변경이나 untracked 파일(무시 목록에 없는 것)이 있으면:
     - 변경된 파일을 짧게 보여준다.
     - 기존 변경과 `/cc` 변경을 구분할 수 없어서 시작할 수 없다고 설명한다.
     - **그대로 진행할지 묻지 않고 중단한다.**
   - `/cc` 자체 상태 파일은 git 디렉터리 안(작업 트리 밖)에 있으므로 이 검사에 걸리지 않는다.

### 3-2. 인터뷰

- 한 번에 질문 하나, 쉬운 말로 묻는다. 사용자가 욕을 하거나 대충 말해도 핵심만 뽑는다.
- 코드·문서로 알 수 있는 건 묻지 않고 직접 확인한다. (`AGENTS.md`, `CLAUDE.md`, `## Yultopia 중점 점검 항목` 절, 관련 코드)
- 정리본에 채울 항목:
  - 목표: 무엇을, 왜
  - 완료 기준: 어떻게 되면 끝인가
  - 범위: 할 것 / 안 할 것
  - 사용자가 이미 정한 방향 (기술 선택, 방식 등)
  - 제약·금지
  - **미리 허락한 위험 작업**: 이 작업에 필요한 위험 작업(DB 쓰기·스키마 변경, 파일·데이터 삭제, 보안·인증·개인정보, 외부 API 계약 변경, 의존성 추가, 배포)을 구체적으로 적는다. 예: "users 테이블에 failed_count, locked_until 컬럼 추가". 해당 작업이 보이면 인터뷰에서 꼭 짚어 묻는다.
  - 검증 방법 (실제 존재하는 테스트·빌드·린트 명령)
- 다 모이면 정리본을 짧게 보여주고 "이대로 시작할까요?"를 묻는다. 사용자가 고치면 반영한다. 승인("ㅇㅇ", "시작" 등)이 나오면 정리본을 active에 저장하고 첫 Codex 호출로 간다.

### 3-3. 마일스톤 루프

Codex는 **마일스톤 단위로만** 부른다. 파일 하나 수정할 때마다, 또는 사소한 단계마다 부르지 않는다.

**첫 Codex 호출**: 정리본을 주고 다음을 한꺼번에 받는다.

- 전체 작업 계획
- 큰 마일스톤 목록
- 각 마일스톤의 완료 기준
- 첫 번째 마일스톤의 구체적인 작업 지시

Claude는 계획 요약과 마일스톤 목록을 화면에 짧게 보여주고, **사용자 승인 없이 바로 첫 마일스톤을 시작한다** (요구사항 정리본을 이미 사용자가 승인했기 때문). 단, 계획이 승인된 정리본의 목표나 범위를 바꾸면 시작하지 말고 사용자에게 묻는다. (사용자 결정)

**마일스톤 하나의 흐름**:

1. Claude가 그 마일스톤 전체를 작업한다. 중간에 Codex를 부르지 않는다.
2. Claude가 검증 명령(지시된 것, 없으면 정리본의 검증 방법)을 실행한다. 출력 원문은 잘라내거나 고치지 않고 active 안에 파일로 저장한다.
3. Claude가 짧은 보고와 함께 Codex를 부른다(같은 Codex 대화 이어서). 보고: 바뀐 파일 목록, 핵심 변경 한두 줄, 검증 결과 한 줄 + 출력 원문 파일 경로, 못 한 것·리스크, 반대 의견(있으면). **diff 본문은 넣지 않는다.**
4. Codex가 실제 diff와 파일을 직접 보고 그 마일스톤을 검수한다.
   - 승인 → 다음 마일스톤의 구체적인 지시를 준다.
   - 반려 → 그 마일스톤만 보완할 내용을 준다. Claude가 보완하고 다시 3으로.
5. 모든 마일스톤이 끝나면 **최종 검수**를 받는다: 전체 변경이 정리본의 목표·완료 기준을 모두 채웠는지.

정상 작업의 Codex 호출 수 = 1(계획) + 마일스톤 수(각 검수, 마지막 것은 최종 검수 포함) + 반려 횟수 + 사용자 확인 질문 수.

**Codex 지시를 받았을 때 Claude의 판단** (정리본에 없는 것만 멈춘다, 사용자 결정):

- 정리본의 「미리 허락한 위험 작업」에 있는 작업 → 멈추지 않고 진행한다.
- 거기에 없는 위험 작업 → **멈추고 사용자에게 묻는다.**
- 정리본의 목표·범위·사용자가 정한 방향을 바꾸는 지시 → **멈추고 묻는다.**
- 범위 안의 작은 단계(테스트 추가, 작업에 필요한 작은 정리 등) → 멈추지 않는다.
- 사용자가 중간에 승인한 위험 작업은 정리본에 추가해서 다음부터는 묻지 않는다.
- Claude가 지시가 기술적으로 틀렸다고 판단하면, 그 부분은 구현하지 않고 보고에 반대 이유를 적어 Codex에게 보낸다. Codex가 같은 지시를 다시 고집하면 사용자에게 묻는다.
- Codex가 `ask_user`를 내면 Codex의 질문임을 밝히고 사용자에게 그대로 묻고, 답을 Codex에게 전달한다.

### 3-4. 멈춤 조건

- 같은 마일스톤에서 **연속 반려 3회** → 멈추고, 무엇이 반복해서 반려되는지 요약해 사용자에게 어떻게 할지 묻는다.
- **전체 Codex 호출 20회** 도달 → 멈추고 묻는다. 이것은 안전장치다. 정상 작업에서는 위의 마일스톤 단위 호출만 일어난다.
- Codex 호출 한 번의 **실행 시간 상한은 20분**이다. (사용자 결정)
  - 20분을 다 쓴 시간 초과 → **자동 재시도하지 않는다.** Codex 프로세스 그룹을 종료하고 사용자에게 보고한다.
  - 실행 직후 생긴 명확한 기술 오류(프로세스가 바로 비정상 종료, 실행 파일·인증·네트워크 오류 등) → 1회 재시도. 또 실패하면 멈추고 보고한다.
  - 잘못된 JSON → 같은 Codex 대화에 형식만 고쳐 다시 달라고 1회 요청. 또 실패하면 멈추고 보고한다.
  - 어느 경우든 active는 남긴다.
- 사용자가 끊으면(Esc 등) → 진행 중인 Codex 프로세스를 종료한다(6장). 사용자가 방향을 바꾸면 그 내용을 정리본에 반영하고, Codex에게 "사용자 지시"로 전달한 뒤 이어 간다. **사용자의 말이 Codex 지시보다 항상 우선이다.**

### 3-5. 완료와 정리

1. Codex가 `done`을 내도 **바로 지우지 않는다.**
2. Claude가 최종 결과를 사용자에게 보여준다: 마일스톤별 결과, 바뀐 파일, 검증 결과, Codex가 남긴 지적(있으면), Codex 토큰 사용량.
3. 사용자에게 완료 여부와 커밋 여부를 묻는다. 커밋은 사용자가 하라고 할 때만 한다. 푸시는 하지 않는다(따로 지시하면 예외).
4. 사용자가 **완료라고 확인하면** active 폴더를 삭제한다.
5. 사용자가 **추가 수정을 요구하면** 같은 active 작업을 이어간다. 그 요구는 Codex에게 사용자 지시로 전달해 새 마일스톤으로 처리한다.

### 3-6. 진행 보고

- 단계가 바뀔 때마다 한 줄. 예:
  - `[cc] Codex 계획: 마일스톤 3개 (1 실패 횟수 저장 / 2 잠금 처리 / 3 테스트)`
  - `[cc 1/3] Claude 작업 중`
  - `[cc 1/3] Codex 검수 중`
  - `[cc 1/3] Codex 반려 (1/3): 잠금 해제 시간이 없음`
  - `[cc 2/3] Codex 승인 → 다음: 잠금 처리`
- 같은 단계가 10분 넘게 이어지면 **10분마다 짧은 생존 보고**: 경과 시간, 지금 하는 일, 살아 있는지(Codex 프로세스 생존 여부와 마지막 활동 시각).
- 구현 방법: Claude는 도구 호출이 끝나야 말할 수 있다. Codex는 백그라운드로 띄우고, Claude는 "최대 약 9분 기다렸다 한 줄 상태나 최종 JSON을 돌려주는" 대기 명령을 반복 호출하면서 그 사이에 보고한다. (Bash 도구 1회 최대 10분 제한 안쪽)
- Claude 자신의 구현이 길어질 때도 도구 호출 사이사이에 대략 10분마다 한 줄 보고한다.

## 4. Codex 호출

### 4-1. 모델과 추론 강도

- Codex 모델과 추론 강도는 **사용자의 기존 Codex 설정(`~/.codex/config.toml` 등)을 그대로** 쓴다.
- 토큰을 줄인다는 이유로 모델이나 추론 강도를 낮추거나 덮어쓰지 않는다.
- `-m`, `model_reasoning_effort` 같은 옵션을 지정하지 않는다. 실제 Codex smoke test(8장)도 같다.
- 별도로 강제할 수 있는 설정은 **읽기 전용 보장을 위한 sandbox 설정뿐**이다.
- 사용자의 현재 설정은 추론 강도가 높아 한 번 호출에 몇 분 걸릴 수 있다. 10분 생존 보고로 커버한다.

### 4-2. 호출 방식

- 첫 호출: `codex exec`. 이후: `codex exec resume <세션ID>`. 같은 Codex 대화를 이어 쓰므로 Codex가 앞 내용을 기억하고, 정리본을 다시 보내지 않는다.
- **읽기 전용 강제**: `exec` 는 `-s read-only`. `resume` 에는 `--sandbox` 옵션이 없으므로 `-c sandbox_mode="read-only"` 같은 설정 덮어쓰기로 강제한다. **이 방법이 실제로 먹히는지 검증한다(8장).** 안 먹히면 다른 방법을 찾고, 못 찾으면 사용자에게 알린다. Codex 쓰기 차단은 필수 요건이다.
  > 2026-10-18 변경 (R31): 읽기 전용 대신 `workspace-write` 로 실행하고, 실행 전후 작업 트리 비교로 Codex의 프로젝트 파일 수정을 잡는다. 10장 참고.
- 읽기 전용의 목적은 **Codex가 코드를 고쳐 Claude 작업과 꼬이는 것을 막는 것**이다. 사용자 Codex 설정에 켜져 있는 MCP 서버(playwright, chrome-devtools)와 플러그인은 끄지 않는다(설정 그대로 원칙). 이들은 샌드박스 밖에서 돌지만 프로젝트 코드를 고치는 도구가 아니므로 허용하고, PM 프롬프트에서 "어떤 도구로도 프로젝트 파일을 만들거나 고치지 말 것"을 명시한다.
- 출력: `--output-schema <스키마>` + `-o <파일>` 로 마지막 메시지(JSON)를 active 안 파일로 받는다.
- `--json` 이벤트 스트림은 **active 안 로그 파일에만** 저장한다. 세션 ID 추출, 마지막 활동 시각, 토큰 사용량 기록에 쓴다. 이벤트 이름·구조는 실제 출력으로 확인한다.
- stdin 은 반드시 닫는다(`</dev/null`). 안 닫으면 입력 대기로 무한정 멈춘다.
- `resume` 에는 작업 폴더 지정 옵션(`-C`)이 없으므로 저장소 루트에서 실행한다.
- 확인된 환경: codex-cli 0.163.0. `exec`, `exec resume`, `--json`, `-o`, `--output-schema`, `-s` 존재 확인함.

### 4-3. Claude 컨텍스트로 돌아오는 것

- 대기 명령은 **진행 상태 한 줄** 또는 **최종 JSON 결과**만 출력한다.
- JSONL 이벤트 로그 전문, Codex의 중간 메시지, 명령 실행 출력은 Bash 출력이나 Claude 응답에 넣지 않는다. 필요하면 파일 경로만 알려준다.

### 4-4. Codex 출력 형식 (JSON)

| 필드 | 설명 |
|---|---|
| `verdict` | `plan` (첫 호출) / `approve` (현재 마일스톤 승인 + 다음 지시) / `reject` (현재 마일스톤 보완) / `done` (최종 검수 통과) / `ask_user` |
| `summary` | 화면에 보여줄 한 줄 요약 (한국어) |
| `plan` | 전체 계획 요약 + 마일스톤 목록(번호, 이름, 완료 기준). `plan` 일 때 필수. `approve` 때 계획을 바꾸면 갱신본 |
| `milestone` | 지금 지시하는 마일스톤 번호 |
| `instruction` | 해당 마일스톤의 구체적 지시. 목표, 수정 범위, 지킬 것, 금지, 검증 명령, 완료 기준. `plan`/`approve`/`reject` 일 때 |
| `findings` | 반려·지적 목록. 항목마다 파일, 줄(가능하면), 내용, 근거. `reject` 일 때 필수, `done` 일 때 남은 사소한 지적 |
| `question` | 사용자에게 물을 것. `ask_user` 일 때 |

- Codex가 `approve` 에서 마일스톤 계획을 바꾸면 Claude는 바뀐 점을 한 줄 보고한다. 목표·범위가 바뀌면 3-3 규칙대로 멈추고 묻는다.
- 세부 필드명·필수 여부는 빌더가 정한다.

### 4-5. PM 역할 프롬프트에 들어갈 내용

- 역할: PM·지시자·검수자. **직접 구현 금지, 어떤 도구로도 프로젝트 파일 생성·수정 금지.** 사용자 지시가 최우선.
- 정리본 전문 (첫 호출에만)
- 진행 방식: 마일스톤 단위. 첫 응답에서 전체 계획·마일스톤·완료 기준·첫 마일스톤 지시를 한꺼번에. 마일스톤을 잘게 쪼개지 말 것.
- 검수 방식: Claude 보고를 믿지 말고 `git diff`·파일과 저장된 검증 출력 원문을 직접 확인. Codex는 테스트·빌드를 다시 돌리지 않는다(읽기 전용이라 캐시·결과 파일 쓰기에서 권한 오류가 난다). 권한 오류로 실패한 명령을 근거로 반려하지 말 것. 근거 없는 지적 금지, 추정은 추정이라고 표시. 정리본의 완료 기준을 모두 채웠을 때만 `done`.
  > 2026-10-18 변경 (R31/R32): Codex는 테스트·빌드·린트를 직접 돌려 확인한다. 권한 오류 관련 문구는 없어졌다. 10장 참고.
- 프로젝트 규칙: Codex는 실행 위치의 `AGENTS.md` 를 스스로 읽는다. `## Yultopia 중점 점검 항목` 절이 있으면 그것을 검수 우선순위로 삼으라고 명시한다.
- 언어: 한국어.
- 문체: codex-plugin-cc 의 `skills/gpt-5-4-prompting` 처럼 XML 블록(`<task>`, `<structured_output_contract>`, `<grounding_rules>` 등)으로 짧고 구조적으로 쓴다.

## 5. 상태 저장과 찌꺼기 정리

### 5-1. 위치

- `<git-dir>/yultopia-cc/active/`
- `<git-dir>` 는 `git rev-parse --git-dir` 로 구한다(절대 경로로 정규화. `--absolute-git-dir` 사용 가능). 작업 트리 밖이므로 `git status`·`git diff` 에 섞이지 않고, 프로젝트 `.gitignore` 를 건드릴 필요가 없다.
- 기존 설계의 `<프로젝트>/.claude/cc/` 방식은 쓰지 않는다.

### 5-2. 내용

active 안에 저장한다.

- 요구사항 정리본
- Codex 세션 ID
- 현재 마일스톤, 마일스톤 계획
- 전체 호출 횟수, 마일스톤별 연속 반려 횟수
- 실행 중 Codex의 PID, 프로세스 그룹 ID, 프로세스 시작 시각 (실행 중인 호출이 없으면 비어 있음을 명시적으로 기록)
- 마지막 활동 시각 `last_activity_at` (상태 파일 안의 값. 상태가 바뀌거나 Codex 이벤트가 올 때마다 갱신)
- Codex JSONL 이벤트 로그, 호출별 JSON 결과
- Claude의 검증 출력 원문
- Codex 토큰 사용량 누계

### 5-3. 규칙

- 저장소마다 active 작업은 **최대 하나**.
- 작업 이력을 쌓는 history 폴더는 만들지 않는다.
- Codex가 `done`을 내도 즉시 삭제하지 않는다. 사용자가 완료라고 확인하면 삭제한다(3-5).
- 사용자가 추가 수정을 요구하면 같은 active를 이어간다.
- 중단, 오류, Claude 세션 종료 시에는 재개를 위해 active를 남긴다.
- 다음 `/yultopia:cc` 실행 때 active가 있으면 이어 하기 / 버리기를 묻는다. 버리기면 삭제 후 새 작업.
- 오래된 active는 5-4 규칙으로 자동 삭제한다.
- **삭제 안전 규칙**: 삭제는 확인된 `<git-dir>/yultopia-cc/active` 정확한 경로에만 한다. `active` 나 `yultopia-cc` 가 심볼릭 링크이거나, 경로가 `<git-dir>` 아래가 아니거나, 그 밖에 비정상이면 삭제하지 말고 중단한다. (SessionStart 훅에서는 "중단" 대신 경고만 하고 넘어간다)

이 방식이면 정상 완료 기록은 바로 없어지고, 중단된 작업도 하나만 남는다.

### 5-4. 오래된 기록 자동 삭제 (14일)

- **언제**: `/yultopia:cc` 실행 때, 그리고 Yultopia의 **SessionStart 훅**(기존 인수인계서 주입 훅과 같은 시점)에서. 별도 cron, launchd, 상시 백그라운드 프로세스는 만들지 않는다.
- **대상**: 현재 저장소의 `<git-dir>/yultopia-cc/active` 하나. (SessionStart 훅은 세션이 시작된 프로젝트의 저장소만 본다. 다른 저장소의 기록은 그 저장소에서 세션이 시작되거나 `/cc` 가 실행될 때 정리된다)
- **만료 판단**: 파일 mtime이 아니라 상태 파일의 `last_activity_at` 값으로 한다. 14일이 넘었을 때만 만료로 본다.
- **삭제 조건** (모두 만족할 때만 삭제):
  1. `last_activity_at` 이 14일을 넘었다.
  2. 그 작업에 기록된 Codex 프로세스가 실제로 살아 있지 않다. 다음 중 하나로 **확실히** 판단될 때만 "살아 있지 않음"으로 본다.
     - 실행 중인 호출이 없다고 상태에 명시적으로 기록돼 있다.
     - 기록된 PID가 존재하지 않는다.
     - 기록된 PID는 있지만 시작 시각·명령 이름이 저장값과 달라 다른 프로세스가 재사용한 것이 확실하다.
  3. 삭제 안전 규칙(5-3)을 통과한다.
- **삭제하지 않고 경고만 하는 경우**:
  - 기록된 Codex 프로세스가 살아 있다.
  - PID 검증이 불확실하다 (상태 파일을 읽을 수 없음, `last_activity_at` 이 없거나 형식이 틀림, 프로세스 정보를 조회할 수 없음 등).
  - 경로가 비정상이다.
- **알림**: 삭제했으면 "오래된 `/cc` 중단 기록을 정리했습니다" 한 줄. 경고는 무엇 때문에 지우지 않았는지 한 줄.
- **SessionStart 훅 제약**: 빨리 끝나야 하고(Codex를 부르지 않는다, 프로세스를 죽이지 않는다), 어떤 경우에도 세션 시작을 깨뜨리지 않는다(항상 정상 종료). 알림은 사용자에게 보이는 방식으로 낸다. 기존 인수인계서 주입 기능과 함께 동작해야 한다.

## 6. 중단 처리 (프로세스)

사용자가 Esc로 중단했을 때 대기용 셸만 죽고 Codex가 뒤에서 계속 돌면 안 된다. 셸 방식으로 구현하되 다음을 지킨다.

- Codex 프로세스를 **별도 프로세스 그룹**으로 실행한다. (macOS에는 `setsid` 명령이 기본으로 없으므로 다른 방법이 필요하다. 빌더가 확인)
- PID와 가능하면 프로세스 그룹 ID, 프로세스 시작 시각을 active 상태에 저장한다.
- 대기 스크립트가 **SIGINT 또는 SIGTERM**을 받으면 해당 Codex 프로세스 그룹도 종료한다.
- 종료 전에 **PID 검증**: 저장된 PID가 아직 살아 있고, 시작 시각과 명령 이름(codex)이 저장값과 일치할 때만 죽인다. 이미 끝났거나 다른 프로세스가 재사용한 PID는 건드리지 않는다.
- Codex 호출마다 **실행 시간 상한 20분**. 넘으면 프로세스 그룹을 종료하고 재시도 없이 보고한다(3-4). 대기 명령이 죽어 있어도 상한이 지켜지도록, 상한 감시는 Codex를 띄운 쪽(대기 명령이 아닌 쪽)이 맡는다.
- **받아들인 제한** (사용자 결정): Esc를 누른 시점에 대기 명령이 돌고 있지 않거나 강제 종료(SIGKILL)로 끊기면 Codex가 즉시 종료되지 않을 수 있다. 대신 아래 세 가지를 **반드시 구현하고 테스트한다.**
  1. 실행 시간 상한 20분 (위)
  2. **다음 사용자 메시지에서 고아 프로세스 확인**: Codex가 살아 있는데 그것을 기다리는 대기 명령이 일정 시간(예: 60초) 넘게 없으면 고아로 본다. 사용자가 다음 메시지를 보내면 UserPromptSubmit 훅이 이를 감지해 Claude에게 알리고(훅은 죽이지 않는다), Claude는 사용자 말에 맞춰 종료하거나 다시 기다린다. 대기 명령의 PID와 마지막 대기 종료 시각도 상태에 기록한다.
  3. **다음 `/cc` 실행 시 확인**: active 상태와 실제 프로세스 생존 여부를 확인한다. 살아 있는 고아 Codex 프로세스가 있으면 사용자에게 알리고 종료한 뒤 재개 여부를 판단한다.

## 7. 플러그인에 추가·수정할 것

이름은 제안이고 빌더가 바꿔도 된다.

- Codex 출력 JSON 스키마 파일
- PM 역할 프롬프트 템플릿 파일
- 스크립트 실행마다 권한 확인이 뜨지 않도록 SKILL.md `allowed-tools` 설정

## 10. 2026-10-18 변경 — Codex가 테스트를 직접 돌린다 (R31/R32)

사용자 결정(2026-10-18): "코덱스도 테스트 돌려야됨. collab 쓸 때처럼 코덱스가 맞을 때까지 기획이나 개발을 검수하고 반려하고 승인하고 책임지고 지시하고, 너(Claude)는 구현하고 수정." 질문으로 정한 것:

- Codex에 쓰기 권한을 주어 실제 프로젝트(설치된 node_modules 등 그대로)에서 테스트를 돌리게 한다. 대신 Codex 실행마다 작업 트리를 전후로 비교해 Codex가 프로젝트 파일을 바꿨으면 바로 멈추고 사용자에게 알린다. 자동으로 되돌리지 않는다. git이 무시하는 파일(캐시, 커버리지, 빌드 결과물)은 바뀌어도 된다. Codex sandbox 의 네트워크는 Codex 기본값(막힘) 그대로 둔다.
- 루프 상한은 그대로: 같은 마일스톤 연속 반려 3회면 사용자에게 묻고, 작업 하나에 Codex 호출 20회.

**R31 — sandbox.** `exec` 는 `-s workspace-write`, `resume` 은 `-c sandbox_mode="workspace-write"`. 모델·추론 강도 인자는 여전히 넣지 않고, 네트워크 설정도 덮어쓰지 않는다. (4-1의 "읽기 전용 보장을 위한 sandbox 설정뿐", 4-2의 "읽기 전용 강제", 9장의 "Codex는 읽기 전용"을 대체한다.)

**R32 — 수정 감시.** 감독 프로세스가 codex 를 실행할 때마다(첫 실행, 빠른 실패 재실행, 형식 재요청) 실행 직전과, codex 가 끝나고 그룹을 정리한 뒤(정상 종료·실패·시간 상한·중단 신호 모두) 작업 트리 스냅샷(추적 파일 + 무시되지 않은 새 파일, 사용자 인덱스는 건드리지 않음)을 떠서 비교한다.

- 바뀌었으면 그 호출은 끝 상태 `codex_modified` 로 끝난다: 재시도·형식 재요청 없음, 결과 JSON 을 상태에 반영하지 않음, `phase=failed`. `last_call.message` 는 한 줄(`[cc] Codex가 프로젝트 파일을 바꿨습니다(되돌리지 않음) — Codex 실행 중에 바뀐 파일: …(최대 10개, 외 N개) · 확인: git diff <pre> <post>`)이고 `last_call.pre_tree`/`post_tree` 에 두 트리를 남긴다. `wait` 는 이 줄을 3 으로 돌려준다. 중단 신호로 끊긴 실행에서 바뀐 것이 잡히면 `wait`(130)·`check-orphan --kill` 의 줄 끝에 같은 내용이 붙는다. 아무것도 되돌리거나 지우지 않는다.
- Codex가 도는 동안 사용자가 직접 고친 파일도 같이 잡힌다. 그래서 메시지는 "Codex 실행 중에 바뀐 파일" 이라고 쓴다.
- 스냅샷을 뜰 수 없으면 확인할 수 없는 것으로 본다: 실행 전이면 codex 를 실행하지 않고, 실행 뒤면 결과를 반영하지 않고, 확인하지 못했다는 한 줄로 끝낸다(`error`).

**프롬프트.** 4-5의 "Codex는 테스트·빌드를 다시 돌리지 않는다 … 권한 오류로 실패한 명령을 근거로 반려하지 말 것"을 대체한다: Codex는 프로젝트의 테스트·빌드·린트 명령을 직접 실행하고 diff 를 읽어 확인한다(검수 때는 반드시). git이 무시하는 파일만 생겨도 되고, 그 밖의 프로젝트 파일은 만들거나 고치거나 지우지 않는다(하나라도 바뀌면 작업이 멈춘다). 네트워크가 막혀서만 실패한 명령은 반려 근거가 아니며 findings 에 그렇다고 적는다. Codex는 여전히 PM·지시자·검수자로서 정리본의 완료 기준을 채웠을 때만 승인하고, 반려할 때는 구체적인 보완 지시를 준다. 사용자 말이 우선이다.

**Claude 절차(SKILL).** Claude는 여전히 검수 요청 전에 검증 명령을 돌려 출력 원문을 저장한다(Codex가 이것과 비교한다). `wait` 가 Codex의 파일 수정을 알리면 멈춰서 그 줄과 `git diff <pre> <post> --stat` 을 보여주고, 아무것도 되돌리지 않았다고 설명한 뒤 어떻게 할지(그대로 둘지, 사용자가 직접 되돌릴지) 묻는다. 자동으로 이어 가지 않는다. 같은 날 사용자 요구로, Codex 결과가 올 때마다 한 줄 요약 대신 Codex 답변 자체(판정, 요약, 지시, 지적 전부)를 그대로 보여주고 다음에 할 일을 쉬운 말 한두 문장으로 설명한다.

**검증.** 가짜 Codex 자동 테스트에 추적 파일 수정·새 파일·무시되는 파일만 쓰기·빠른 실패 재실행·형식 재요청·시간 상한·중단·스냅샷 실패 경우를 더했다. 실제 Codex smoke test(8-2)의 2단계는 "resume 에서도 쓰기가 막히는지" 대신 `workspace-write` 인자와 "프로젝트 파일이 바뀌지 않았는지(`codex_modified` 아님, git status 깨끗함)" 를 확인한다.

**Codex 1차 검수 반영 (같은 날).** Codex(PM)가 위 구현을 반려하며 지적한 네 가지를 고쳤다.

1. 하위 모듈: 작업 트리 스냅샷이 초기화된 하위 모듈(중첩 포함)을 재귀적으로 뜬다. 하위 모듈의 작업 트리가 그 HEAD 와 다르면 gitlink 를 "HEAD + 하위 모듈 스냅샷 tree" 로 만든 고정된 합성 값으로 바꾸므로, 하위 모듈 안의 수정·삭제·새 파일이 최상위 diff 에 하위 모듈 경로로 나온다. 무시된 파일만 바뀌면 그대로이고, 사용자 인덱스(하위 모듈 포함)는 건드리지 않는다. 임시 인덱스는 스냅샷마다 따로 만든 임시 폴더에 둔다(끊긴 스냅샷이 남긴 잠금 파일과 겹치지 않음).
2. 종료를 확인하지 못한 호출: 그룹이 비었음을 확인하지 못했으면(R30 `stop_failed`) 그 순간 바뀐 것이 없어도 안전하다고 보지 않는다. 결과를 반영하지 않고(정상 응답이어도 `error`, phase failed, verdict null), 재시도도 하지 않으며 `running.stop_failed` 를 남긴다. 그룹이 확실히 사라진 뒤 정리하는 쪽이 저장된 실행 전 트리로 다시 비교해 바뀌었으면 `codex_modified`, 스냅샷 실패면 확인 실패 `error` 로 고친다.
3. 실행 전 트리의 저장: 감독 프로세스는 시도마다 실행 전 트리를 codex 를 띄우기 전에 `running.pre_tree` 로 원자적으로 남긴다(못 남기면 실행하지 않음). 감독 프로세스가 끝 상태 없이 죽었거나(중단 처리의 유예 10초를 넘겨 KILL 등) 2의 기록이 확실히 끝났으면 `wait`·`check-orphan`(--kill 포함)·preflight·다음 `call` 이 이것으로 다시 비교해 기록한다(`call` 은 새로 바뀐 것을 찾으면 그 줄과 6). 메시지마다 도는 훅은 빨라야 하므로 스냅샷을 뜨지 않고 그런 기록을 그대로 둔다.
4. 실행 뒤 스냅샷 실패는 끝난 원인(시간 초과, 중단, 고아 종료)과 상관없이 `error`·phase failed·verdict null 로 기록하고 메시지에 원인과 확인 실패를 함께 적는다. 신호를 받은 `wait` 자신의 130 은 그대로다.

**Codex 2차 검수 반영 (같은 날).** 종료를 확인하지 못한 호출에서 첫 비교가 이미 바뀐 것을 찾았어도(`codex_modified`, `stop_failed`) 그룹이 확실히 사라진 뒤 저장된 실행 전 트리로 최종 작업 트리를 다시 비교한다. 최종 트리가 기록과 다르면 `post_tree` 와 한 줄 메시지(바뀐 파일 목록, `git diff <pre> <post>`)를 최종 값으로 고친다(남은 프로세스의 나중 변경까지 포함). 같거나 마지막 스냅샷이 실패해도 앞서 찾은 증거(상태·트리·파일)는 지우지 않고, "추가로 바뀐 파일 없음" 또는 확인 실패를 같은 줄에 덧붙인다. 처음 알릴 때도 "남은 Codex 프로세스가 끝난 뒤 다시 확인합니다" 를 붙인다. wait·check-orphan(--kill 포함)·preflight·다음 call 모두 같은 정리 함수를 거친다.

**Codex 3차 검수 반영 (같은 날).** (1) 그룹이 사라진 것을 확인하고 최종 비교를 마친 기록에는 감독 프로세스가 붙였던 앞으로의 안내("다시 확인합니다"), 종료 미확인 경고, `ps` 안내를 남기지 않는다. 이미 `codex_modified` 였던 기록은 저장된 pre/post 트리로 증거 한 줄을 다시 만들고 최종 결과("추가로 바뀐 파일 없음", "지금 작업 트리는 실행 전과 같음", "다시 확인하지 못함: …")만 붙인다. 그래서 다시 `wait` 해도 더 기다리라는 말이 없다. (2) 14일 자동 정리도 지우기 전에 같은 최종 비교를 한다(사용자가 부른 preflight·cleanup-stale 에서만, last_activity_at 유지). Codex의 수정이나 최종 확인 실패를 새로 찾으면 그때는 지우지 않고 그 한 줄을 `stale_notice` 로 알린다. 세션 시작 훅은 지금처럼 스냅샷 없이 정리한다.

**Codex 4차 검수 반영 (같은 날).** (1) 끝난 호출 기록을 정리하며 최종 비교한 결과를 state 에 기록하지 못하면(잠금 실패·쓰기 실패 등으로 그 호출의 running 이 그대로 남음) 실패로 본다: 다음 `call` 은 새로 부르지 않고 한 줄 오류(1)를 내고, preflight·cleanup-stale 의 14일 정리는 지우지 않고 "최종 비교 결과를 기록하지 못해 지우지 않았습니다" 한 줄을 알린다. 그래서 첫 정리 동안만 잠겨 있다 풀려도 이전 호출의 실행 전 트리를 덮어쓰거나 지우지 않는다. (2) 처음 실행 뒤 스냅샷이 실패했던 호출도 최종 다시 비교가 되면 그 확인 실패 문구를 지우고 최종 결과만 남긴다. 최종 비교도 실패하면 확인 실패를 정확히 한 번만 적는다.

**2026-10-18 보안 수정 (R33/R34).** 자동 보안 검토가 위 수정 감시의 두 가지 문제를 찾았고, 사용자가 권장안을 골랐다. 실행 뒤 비교는 감독 프로세스(Claude 권한, Codex sandbox 밖)가 git 을 돌리는 일이라, Codex가 쓸 수 있는 것(작업 트리, 어쩌면 `.git`)은 모두 믿지 않는 입력으로 본다.

- **R33 — 중첩 저장소와 git 설정 ("막기").** (1) 스냅샷은 실행 전부터 있던 등록된 하위 모듈 안에서만 git 을 실행한다: HEAD 의 tree 에 gitlink 로 있고, `git config --blob HEAD:.gitmodules` 에 그 경로가 있고(작업 트리의 `.gitmodules` 는 보지 않는다), 그 경로의 `.git` 이 gitfile 이며 가리키는 git 디렉터리의 실제 경로가 `$(git rev-parse --absolute-git-dir)/modules/` 아래일 때. 그 밖의 중첩 저장소(새로 생긴 것, 등록되지 않은 것, git 디렉터리가 다른 곳인 것)는 그 안에서 git 을 실행하지 않고 그 경로에 고정된 표시 gitlink 하나로 남긴다. 그래서 생기거나 없어지면 `codex_modified` 로 그 경로가 나온다. 원래 있던 그런 저장소는 전후 같은 표시라 그 안의 변경은 보지 않는다(한계). `git add -A` 는 gitlink 폴더와 중첩 저장소를 pathspec 으로 빼고 부른다(그 안에서 `git status` 를 돌리거나 커밋 없는 저장소에서 실패하지 않도록). (2) 스냅샷·diff 의 모든 git 은 명령줄 범위 설정으로 굳힌다: `core.fsmonitor=false`, `core.hooksPath=/dev/null`, `core.untrackedCache=false`, `submodule.recurse=false`, `GIT_CONFIG_NOSYSTEM=1`(`git -c` 와 같은 범위인 `GIT_CONFIG_COUNT` 환경변수로 준다. 하위 모듈 git 에도 간다), diff 에는 `--no-ext-diff --no-textconv`. preflight·init 의 작업 트리 확인(`git status`)도 같다. 저장소 설정에 사용자가 둔 filter 드라이버(git-lfs 등)는 그대로 돈다. (3) git 설정 지문: codex 를 실행할 때마다 실행 전에 `.git/config`(worktree 면 공통 설정과 `config.worktree`), `info/attributes`, `info/exclude`, `.git/modules` 아래 폴더와 모든 하위 모듈 git 디렉터리의 설정, 이 설정들의 `include.path`/`includeIf` 대상(없는 대상 포함), 작업 트리의 `.git` 자체를 기록해 `running.pre_gitcfg` 에 둔다. codex 가 끝나면 어떤 git 명령보다 먼저 git 없이 다시 계산해 비교하고, 다르면 실행 뒤 스냅샷을 아예 뜨지 않고 `codex_modified` 로 끝낸다(결과 반영 없음, 되돌리지 않음, `last_call.gitcfg_changed`, `post_tree` 없음, 한 줄 "Codex가 git 설정을 바꿨습니다(되돌리지 않음) — 바뀐 설정 파일: …"). 나중에 다시 비교하는 쪽(wait·check-orphan·preflight·다음 call·14일 정리)도 같은 기록으로 먼저 확인한다. 지문 기록이 없는 기록(이전 버전)은 확인할 수 없는 것으로 본다. SKILL 은 이 줄을 받으면 그 저장소에서 git 명령(`git diff` 포함)을 돌리지 않고, 사용자가 파일을 확인해 정리하기 전에는 다시 부르지 않는다.
- **R34 — 무시된 중요 파일 감시 ("중요한 것만 감시").** git 이 무시하는 파일 중 비밀·설정 파일(`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pypirc`, `.netrc`, `*.keystore`, `credentials*`, `secrets*`, 깊이 상관없음)과 의존성 폴더(`node_modules/`, `vendor/`, `.venv/`, `venv/`, `Pods/`, `.bundle/`, 깊이 상관없음) 안의 파일을 내용으로 감시한다. 목록은 `common.sh` 의 상수 `CC_IGNORED_WATCH_PATTERNS` 하나다. 실행 전 `git ls-files -z -o -i --exclude-standard`(굳힌 설정)로 고른 경로를 git 과 같은 blob id 로 해시한 정렬된 manifest(`calls/<n>/ignored.pre`, 요약값 `running.pre_ignored`)를 남기고 실행 뒤 비교한다. 해시는 직접 계산하고 객체 저장소에 쓰지 않는다. 심볼릭 링크는 따라가지 않고 링크 대상으로, 그 안의 중첩 저장소는 안을 보지 않고 한 항목으로 둔다. 더해지거나 없어지거나 바뀌면 작업 트리가 같아도 `codex_modified`(메시지에 "git이 무시하는 감시 대상 중 바뀐 파일(git diff 에는 안 나옴): …" 최대 10개와 개수, `last_call.ignored_changed`). 그 밖의 무시된 출력(빌드, 캐시, 커버리지, 로그)은 그대로 허용한다. manifest 를 만들거나 비교하지 못하면 스냅샷 실패와 같이 다룬다.
- **보안 수정 후속 (같은 날, 사용자 결정).** (1) "막기" 의 연장: git 설정이 바뀌어 멈춘 호출은 `state.gitcfg_tamper`(바뀐 파일, 그 실행 전 지문)를 남긴다. 이 기록이 있는 동안 `call`(모든 종류), 끝난 기록의 다시 비교(wait·check-orphan·preflight·다음 call·14일 정리), preflight 는 무엇보다 먼저 git 없이 지문을 다시 계산해, 아직 다르면 git 을 하나도 돌리지 않고 한 줄로 거부한다(`call` 은 6, "아직 Codex 실행 전과 다른 설정 파일: … 되돌리거나 작업을 버리세요(discard)"). 14일 자동 정리도 그 기록을 지우지 않는다(세션 시작 훅은 지문을 계산하지 않고 그대로 둔다). 사용자가 되돌려 지문이 다시 같아지면 기록을 지우고 그대로 이어 간다. discard·finish 는 git 을 돌리지 않으므로 그대로 되고, 아직 다르면 완료 줄에 주의를 붙인다. (2) 무시된 파일 감시에서 `node_modules/.cache/` 와 `node_modules/.vite/` (어느 깊이의 node_modules 든) 아래는 뺀다(`common.sh` 의 `CC_IGNORED_WATCH_EXCLUDE`): 테스트·빌드 도구가 돌 때마다 다시 쓰는 캐시라 감시하면 매번 멈춘다. 대신 Codex가 바꾼 캐시를 다음 빌드가 쓸 수 있다(README 에 적음). 그 밖의 node_modules 는 그대로 감시한다.
- **Codex 보안 검수 1차 반영 (같은 날).** (1) 격리 기록을 active 와 따로 둔다: git 설정이 바뀌었거나 그 무결성을 확인하지 못한(기준 지문이 있을 때) 호출은 `<git 디렉터리>/yultopia-cc/gitcfg-quarantine.json`(기준 지문, 바뀐 파일)을 원자적으로 남기고, discard·finish 는 active 만 지운다. cc-codex.sh 는 무엇보다 먼저 git 없이(셸만으로 저장소를 찾아) 이 기록을 확인한다: 아직 다르거나 확인할 수 없으면 git 디렉터리도 git 없이 정하고(`git rev-parse` 도 부르지 않음, 훅 포함) call 모든 종류·preflight(`git_config_changed`)·init·cleanup-stale 을 거부하고, 나머지 명령은 git 없이 동작한다. 기준과 다시 같아질 때만 기록을 지운다. (2) 하위 모듈은 실행 전에 allowlist(HEAD gitlink + HEAD `.gitmodules` + 지금 gitfile 이 가리키는 정확한 `<git 디렉터리>/modules/<이름>`, gitfile 내용)를 만들어 `running.pre_submodules` 에 두고, 실행 전후 스냅샷·manifest 는 그 목록과 똑같은 하위 모듈에만 들어간다. allowlist 가 없는 스냅샷도 `.git/modules` 의 하위라는 것만으로 믿지 않고 정확한 이름의 gitdir 만 믿는다. 모듈 탐색의 깊이·개수 제한, 읽을 수 없는 폴더는 확인 실패로 막는다. (3) 그룹이 비었음을 확인하지 못했으면(stop_failed) 정상·시간 초과·중단 어느 경로에서도 실행 뒤 스냅샷·diff 를 하지 않고(감독 프로세스는 그 뒤 `git rev-parse` 도 부르지 않는다) 결과를 반영하지 않은 채 `running.pre_*` 로 미룬다. 그룹이 사라진 것을 확인한 쪽만 git 없는 설정 확인 → 스냅샷 순으로 비교한다. (4) 무시된 중요 파일 manifest 를 allowlist 의 하위 모듈마다 만들어 `sub/...` 경로로 한 증거로 비교한다(더 믿을 수 없게 된 하위 모듈은 그 안을 보지 않고 바뀐 것으로). (5) 지문 없는 이전 기록이나 지문 확인 오류는 "작업 트리를 확인하지 못해" 와 다른 상태(`last_call.gitcfg_unverified`)·문구("git 설정 무결성을 확인하지 못해 git 명령을 실행하지 않았습니다")로 알리고 git diff 를 권하지 않는다. SKILL 도 그 줄에서 git 명령을 쓰지 않는다.
- **Codex 보안 검수 2차 반영 (같은 날, 컨트롤러 결정 R36).** (1) 격리 기록을 Codex가 바꿀 수 있는 `.git` 아래에서 저장소 밖으로 옮겼다: `${CLAUDE_PLUGIN_DATA:-$HOME/.claude/plugins/data/yultopia}/cc/quarantine/<작업 트리 실제 경로(pwd -P)의 sha256>.json` (state armed·tampered·unverified, 기준 지문, 호출 번호, 작업 트리 경로). 감독 프로세스는 codex 를 실행할 때마다 그 직전에 armed 기록을 원자적으로 쓰고(못 쓰면 codex 를 실행하지 않는다), 종료 확인·지문 확인·실행 뒤 비교·최종 상태 기록이 모두 성공해야 지운다. git 설정이 바뀌었으면 tampered, 확인하지 못하면 unverified 로 남는다(고쳐 쓰지 못해도 armed 가 남아 막는다). 모든 cc-codex.sh 진입점은 git 없이(작업 트리 경로와 그 위 폴더로) 이 기록을 먼저 찾고, tampered·unverified 이거나 armed 인데 지금 지문이 다르면(기록을 읽거나 쓰지 못해도) git 을 돌리지 않는다. 기준과 같고 같은 호출의 running 기록이 남아 있을 때만 실행 뒤 비교를 이어 가며, 비교와 최종 상태 기록을 마친 전용 경로만 armed 를 지운다. running 기록이 없거나 tampered·unverified 상태면 자동 해제하지 않는다. 기록 폴더·파일이 심볼릭 링크이거나 기록 폴더가 작업 트리 안이면 쓰지 않는다. `.git` 아래의 격리 기록(1차)은 뺐다: `.git` 을 gitfile·링크로 바꾸면 그 경로를 믿을 수 없고 링크를 따라 밖에 쓰게 된다. 훅은 이 폴더를 만들지 않고, 기록이 없으면 셸 내장 명령만 쓴다. (2) 지문 없는 이전 기록은 SessionStart를 포함한 모든 자동 정리에서 먼저 기준 없는 unverified 기록으로 남기고 active 를 지우지 않는다. 기록을 남기지 못해도 active 를 지우지 않는다. 사용자가 git 설정과 Codex 실행 중 바뀐 프로젝트 파일을 확인한 뒤 `cc-codex.sh release-quarantine` 으로 지우기 전까지 모든 새 명령이 git 을 쓰지 않는다(discard·finish 뒤에도).
