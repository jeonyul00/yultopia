# cc

사용자는 Claude하고만 말한다. Claude가 인터뷰로 요구사항 정리본을 만들어 승인받은 뒤, Codex CLI(읽기 전용 PM)와 마일스톤 단위로 자동으로 주고받는다. Codex는 계획·검수·승인/반려를 맡고, 코드는 Claude만 고친다. 사용자는 진행 줄을 보다가 방향이 틀리면 끊는다.

## 1. 이 세션의 원칙

- **사용자의 말이 Codex 지시보다 항상 우선이다.** 충돌하면 사용자 말을 따르고 Codex에는 "사용자 지시"로 전한다(6장 "사용자 말 전달").
- 사용자에게는 쉬운 한국어로 짧게 말한다. 전문용어는 풀어 쓴다.
- Codex 쪽 정보는 `cc-codex.sh` 가 출력한 한 줄과 결과 JSON만 쓴다. active 안의 `calls/`, `events*.jsonl`, `stderr*.log`, `supervisor.log` 같은 Codex 로그는 열지도, 붙여 넣지도 않는다.
- 상태 파일(정리본·보고·메시지·검증 출력)은 `.git` 안에 있다. Write·Edit 도구로 쓰지 않는다. 항상 `cc-codex.sh put` 으로 쓴다. `cc-codex.sh path <active|brief|report|message|verify>` 는 사용자에게 위치를 알려 줄 때와, Read 로 읽기만 할 때(이어 하기의 정리본, 실패한 검증 출력 원문)만 쓴다.
- `cc-codex.sh` 는 PATH 에 있다. 경로를 붙이지 말고 이름 그대로 부른다. 그 밖의 명령을 `cc-codex.sh` 를 거쳐 실행하지 않는다.
- 커밋은 사용자가 시킬 때만 한다. 푸시는 하지 않는다(사용자가 따로 시키면 예외).
- 상태 파일 쓰기 형식 (구분자는 `CC_END`. 내용 안에 `CC_END` 한 줄이 없게 한다). 성공하면 `[cc] <이름> 저장됨` 한 줄, 빈 내용은 거부(1)된다. 진행 중인 작업이 없으면 5(작업이 이미 끝났거나 버려짐: 그 줄을 전하고 멈춘다):

  ```bash
  cc-codex.sh put report <<'CC_END'
  (내용)
  CC_END
  ```

## 2. 시작

사용자가 처음 한 말(비어 있을 수 있음): $ARGUMENTS

1. `cc-codex.sh preflight` 를 실행한다. 출력은 JSON 한 줄 `{"ok","code","message","dirty_files","stale_notice","active"}` (0 = 시작 가능, 7 = 시작 불가).
2. `stale_notice` 가 있으면 어떤 `code` 든 그 한 줄을 먼저 전한다.
3. `code` 별로 처리한다:

| code | 할 일 |
|---|---|
| `ready` | 위 원문을 출발점으로 인터뷰(3장)를 시작한다. 비어 있으면 "무엇을 할까요?" 한 줄만 묻는다. |
| `not_git`, `no_jq`, `no_codex`, `not_logged_in` | `message` 를 쉬운 말로 전하고 끝낸다. |
| `dirty` | `dirty_files` 가 비어 있으면(작업 트리 확인 자체가 실패) `message` 를 그대로 전하고 끝낸다. 있으면 `message`(변경 개수 포함)와 `dirty_files`(최대 10개)를 짧게 보여주고, "기존 변경과 /cc 변경을 구분할 수 없어 시작할 수 없다"고 설명한 뒤 **묻지 않고** 끝낸다. 커밋·stash 를 대신 하지 않는다. 정리한 뒤 다시 실행하면 된다고만 알린다. |
| `orphan_running` | 아래 "고아 Codex". |
| `active_present` | 아래 "남은 작업". |

**고아 Codex** (`orphan_running`):
- `message` 에 "확인할 수 없는 프로세스가 프로세스 그룹" 이 있으면: /cc 가 이것을 자동으로 종료하지 않는다고 알리고, 직접 확인하는 명령 `ps -o pid,command -g <pgid>` 를 보여준 뒤 끝낸다. 죽이지 않는다.
- 아니면: "기다리는 쪽 없이 돌던 이전 Codex를 종료합니다" 라고 알리고 `cc-codex.sh check-orphan --kill` 의 출력 한 줄을 전한다. exit 0 이거나 줄이 "종료했습니다"·"이미 끝나 있었습니다" 면 preflight 를 한 번 더 한다. 그 밖의 줄(KILL 뒤에도 남음, 확인하지 못해 종료하지 않음)이나 exit 1 이면 끝낸다. 다시 해도 `orphan_running` 이면 끝낸다.

**남은 작업** (`active_present`): `active` 가 있으면 단계(`phase`), 마일스톤(`milestone`/`milestones_total`), 마지막 활동 시각을 한 줄로 보여준다(상태를 읽을 수 없으면 `active` 는 null 이다).
- `message` 가 "이어 하거나 버릴 수 있습니다" → "이어 할까요, 버릴까요?" 묻는다.
- "버릴 수만 있습니다" 또는 "상태 파일을 읽을 수 없습니다" → 이어 할 수 없다고 설명하고 버릴지 묻는다. 이런 기록은 Codex가 도는지 알 수 없으므로, 버리기는 이 작업의 Codex 프로세스가 남아 있지 않은지 먼저 확인하고 남아 있거나 확인하지 못하면 지우지 않는다(6: 그 줄에 PID와 `ps -o pid,command -g <pgid>` 가 있으면 그대로 보여주고 끝낸다. 죽이지 않는다).
- "이어 하거나 지울 수 없습니다"(경로 비정상) → 그대로 전하고 끝낸다.
- 버리기: `cc-codex.sh discard`. 0 이면 "코드 변경은 그대로 두었다"고 알리고 preflight 를 다시 한다(이전 변경이 남아 있으면 `dirty` 로 끝난다). 6 이고 줄이 "Codex가 실행 중입니다" 면 사용자가 버리기를 고른 것이므로 9장 "Codex 멈추기" 를 한 뒤 discard 를 한 번만 다시 한다. 6 의 그 밖의 줄이면 Codex가 돌 수 있다는 뜻: 그 줄을 전하고(프로세스 그룹이 적혀 있으면 `ps -o pid,command -g <pgid>` 도) 끝낸다. 1 이면 그 줄을 전하고 끝낸다.
- 이어 하기: 10장.

## 3. 인터뷰

- 질문은 한 번에 하나, 쉬운 말로. 사용자가 거칠게 말해도 핵심만 뽑는다.
- 코드·문서로 알 수 있는 것은 묻지 말고 직접 확인한다: `AGENTS.md`, `CLAUDE.md`, 그 안의 `## Yultopia 중점 점검 항목` 절, 관련 코드, 실제로 있는 테스트·빌드·린트 명령.
- 정리본 항목:
  1. 목표 — 무엇을, 왜
  2. 완료 기준 — 어떻게 되면 끝인가
  3. 범위 — 할 것 / 안 할 것
  4. 사용자가 정한 방향 — 기술 선택, 방식
  5. 제약·금지
  6. 미리 허락한 위험 작업 — 이 작업에 필요한 DB 쓰기·스키마 변경, 파일·데이터 삭제, 보안·인증·개인정보, 외부 API 계약 변경, 의존성 추가, 배포를 구체적으로 (예: "users 테이블에 failed_count, locked_until 컬럼 추가"). 이런 작업이 보이면 꼭 짚어 묻는다. 없으면 "없음".
  7. 검증 방법 — 실제로 있는 명령
- 다 모이면 정리본을 짧게 보여주고 "이대로 시작할까요?" 묻는다. 고치라면 반영해 다시 보여준다.
- 승인("ㅇㅇ", "시작" 등)이 나오면 저장한다:

  ```bash
  cc-codex.sh init <<'CC_END'
  (정리본 전문)
  CC_END
  ```

  0 → 4장. 4(이미 진행 중인 작업이 있음: 다른 세션이 먼저 시작함) → 그대로 전하고 preflight 부터 다시. 1 → 그 줄을 전하고 끝낸다.
  8(커밋되지 않은 변경이 있음: 인터뷰하는 동안 파일이 바뀜) → 그 줄의 파일 목록을 보여주고, 기존 변경과 /cc 변경을 구분할 수 없어 시작할 수 없다고 설명한다. 승인받은 정리본 전문을 답변에 그대로 남겨 두고(사용자가 커밋하거나 stash 한 뒤 `/yultopia:cc` 를 다시 실행할 때 붙여 넣을 수 있게) **묻지 않고** 끝낸다. 커밋·stash 를 대신 하지 않는다.

## 4. 계획

1. `cc-codex.sh call plan` → 대기 루프(8장).
2. `verdict` 가 `plan` 이면 `[cc] Codex 계획: 마일스톤 N개 (1 이름 / 2 이름 / …)` 한 줄과 `plan.overview` 한두 줄을 보여주고, **승인 없이** 바로 마일스톤 1의 `instruction` 을 시작한다(5장). `ask_user` 면 계획 전에 Codex가 묻는 것이다: `Codex 질문: <question>` 으로 그대로 묻고 답은 6장 "사용자 말 전달"로 보낸다(계획 요청의 결과는 이 둘뿐이다).
3. 단, 계획이 승인된 정리본의 목표·범위·사용자가 정한 방향을 바꾸면 시작하지 말고, 무엇이 다른지 보여주고 묻는다. 답은 6장 "사용자 말 전달"로 보낸다.

## 5. 마일스톤 작업

1. `[cc 1/3] Claude 작업 중: <마일스톤 이름>` 같은 한 줄.
2. 그 마일스톤 전체를 끝까지 구현한다. 중간에 Codex를 부르지 않는다(파일 하나, 작은 단계마다 부르지 않는다). 지시는 6장 "정리본과 대조"를 거친 것만 한다.
3. 지시의 검증 명령(없으면 정리본의 검증 방법)을 실행한다. 실패하면 고쳐서 다시 돌린다. 마지막 결과는 출력 원문을 자르거나 고치지 않고 저장한다(검증 명령은 평소처럼 직접 실행하고, 파일 이름은 영문·숫자·`.`·`_`·`-` 만):

   ```bash
   { <검증 명령>; printf '\nexit=%s\n' "$?"; } 2>&1 | cc-codex.sh put verify m<번호>-<이름>.log
   ```

   예: `{ npm test; printf '\nexit=%s\n' "$?"; } 2>&1 | cc-codex.sh put verify m1-test.log`. 출력 줄 끝의 `(exit=N)` 으로 결과를 안다. `(exit=…)` 가 없거나 실패면 `cc-codex.sh path verify` 폴더의 그 파일을 Read 로 읽는다(읽기만).
4. 짧은 보고를 저장한다. diff 본문은 넣지 않는다(Codex가 실제 diff 를 직접 본다):

   ```bash
   cc-codex.sh put report <<'CC_END'
   마일스톤 <번호>: <이름>
   - 바뀐 파일: …
   - 핵심 변경: (1~2줄)
   - 검증: <명령> → 통과/실패 (verify/m1-test.log)
   - 못 한 것·리스크: … (없으면 없음)
   - 반대 의견: … (따르지 않은 지시와 이유. 있을 때만)
   - 사용자 지시·승인: … (이번 마일스톤 중 사용자가 정한 것. 있을 때만)
   CC_END
   ```

5. `cc-codex.sh call review` → `[cc 1/3] Codex 검수 중` → 대기 루프.

## 6. Codex 결과 처리

결과 JSON 필드: `verdict`, `summary`, `plan`, `milestone`, `instruction`, `findings`, `question`. 사용자에게는 `summary` 와 필요한 부분만 짧게 전한다. 진행 줄의 `[cc 1/3]` 은 지금 마일스톤 번호/전체 마일스톤 수다.

**`call review` 의 결과** (마일스톤 검수):
- `approve`: `[cc 2/3] Codex 승인 → 다음: <이름>` 한 줄 → 정리본과 대조 → 다음 마일스톤(5장). `plan` 이 함께 오면 계획이 바뀐 것: 바뀐 점을 한 줄 보고하고, 목표·범위가 바뀌었으면 멈추고 묻는다.
- `reject`: `cc-codex.sh status` 의 "연속 반려 R회" 로 R 을 확인하고 `[cc 1/3] Codex 반려 (R/3): <summary>` 한 줄.
  - R 이 3 미만 → `instruction`·`findings` 를 대조 → 같은 마일스톤을 보완하고 5장 3~5를 다시 한다.
  - R 이 3 이면 보완하지 말고 바로 멈춰 묻는다: 무엇이 반복해서 반려되는지 `findings` 를 요약하고 어떻게 할지. 계속하라면 `cc-codex.sh ack-rejects` → 보완 → 5장 3~5. 방향을 주면 "사용자 말 전달".
- `done`: 11장.
- `ask_user`: Codex의 질문임을 밝히고 `Codex 질문: <question>` 으로 그대로 묻는다. 답은 "사용자 말 전달"로 보낸다.

**`call message` 의 결과** (검수가 아니다. 마일스톤은 `call review` 로만 승인·반려된다):
- `approve`·`reject`·`done`: `[cc 1/3] Codex 답변: <summary>` 한 줄만 보여준다("승인 → 다음"·"반려" 라고 하지 않는다). 정리본과 대조한 뒤 **지금 마일스톤**을 그 `instruction` 대로 이어 간다(지시가 없으면 지금 마일스톤을 마무리한다) → 5장 3~5로 검수를 받는다. `plan` 이 함께 오면 바뀐 점을 한 줄 보고하고, 목표·범위가 바뀌었으면 멈추고 묻는다.
- `ask_user`: 위와 같다.
- `plan`(계획을 처음 내거나 다시 짠 경우): 4장 2~3처럼 처리한다.

**정리본과 대조** (`approve`·`reject`·`plan` 의 지시마다):
- 정리본의 「미리 허락한 위험 작업」에 있는 작업 → 멈추지 않고 진행한다.
- 거기에 없는 위험 작업(DB 쓰기·스키마 변경, 파일·데이터 삭제, 보안·인증·개인정보, 외부 API 계약 변경, 의존성 추가, 배포) → **멈추고 사용자에게 묻는다.**
- 정리본의 목표·범위·사용자가 정한 방향을 바꾸는 지시 → **멈추고 묻는다.**
- 범위 안의 작은 단계(테스트 추가, 작업에 필요한 작은 정리) → 묻지 않고 진행한다.
- 사용자가 중간에 승인한 위험 작업은 정리본에 추가해 전문을 다시 저장한다(`put brief`). 다음부터는 묻지 않는다.
- 지시가 기술적으로 틀렸다고 판단하면 그 부분은 구현하지 않고 보고의 "반대 의견"에 이유를 적는다. Codex가 같은 지시를 다시 고집하면 사용자에게 묻는다.

**사용자 말 전달** (방향 수정, 질문에 대한 답, 추가 요구):
1. 정리본에 들어갈 내용이면 정리본 전문을 고쳐 저장한다:

   ```bash
   cc-codex.sh put brief <<'CC_END'
   (고친 정리본 전문)
   CC_END
   ```

2. 사용자 말을 메시지로 저장하고 `cc-codex.sh call message` → 대기 루프 → 위 "`call message` 의 결과" 대로 처리한다:

   ```bash
   cc-codex.sh put message <<'CC_END'
   사용자 지시: … (질문에 대한 답이면 "사용자 답: …")
   CC_END
   ```

3. `call message` 가 1 이고 "이어 쓸 Codex 세션이 없습니다" 면 아직 계획 전이다: 정리본만 고치고 `call plan`.

## 7. 멈춤

- `call` 이 6 이면 출력 줄로 판단한다:
  - "연속 반려 3회": 6장에서 묻지 못한 경우의 안전망이다(이어 하기 뒤 등). 무엇이 반복해서 반려되는지 요약해 어떻게 할지 묻는다. 계속하라면 `cc-codex.sh ack-rejects` 후 `call review`(이미 보완해 두었으면 다시 보완하지 않는다). 방향을 주면 "사용자 말 전달".
  - "호출 상한 20회": 멈추고 묻는다(지금 상태로 마무리할지, Codex 없이 남은 일을 할지). 더는 Codex를 부를 수 없다.
  - "이미 실행 중": 사용자가 멈추거나 방향을 바꾸라고 해서 그 말을 전하려던 중이면 기다리지 말고 9장 "Codex 멈추기" 를 한 뒤 같은 `call` 을 한 번만 다시 한다. 그 밖에는 새로 부르지 말고 대기 루프로 기다린다(사용자 말을 전하려던 중이었으면 그 결과를 그대로 따르지 말고, 받은 뒤 이어서 사용자 말을 전한다).
  - "기록이 깨져 있어": 그대로 전하고 `cc-codex.sh discard` 로 버릴지 묻는다.
  - "끝났는지 확인하지 못해": 이전 호출의 Codex 프로세스가 아직 남아 있을 수 있어 새로 부르지 않았다는 뜻이다. 그 줄을 전하고 `ps -o pid,command -g <pgid>` 로 직접 확인할 수 있다고 알린 뒤 멈춘다. 다시 부르지 않는다(남은 것이 정말 없어지면 다음 `call` 이 그대로 된다).
- `call` 이 1 이면 그 줄을 전하고 멈춘다. 입력 파일이 없다는 줄이면 `put` 으로 다시 저장하고 한 번만 다시 부른다.
- `wait` 가 3 이면 그 한 줄(시간 초과, 기술 오류, 형식 오류, 중단 기록 등)을 전하고 멈춘다. 시간 초과는 자동으로 다시 부르지 않는다. 사용자가 다시 하라면 같은 종류로 다시 부른다. 줄에 "끝났는지 확인하지 못했습니다" 가 있으면 Codex 프로세스가 남아 있을 수 있다는 것도 함께 알린다(그 줄의 `ps -o pid,command -g <pgid>` 로 확인).
- 어떤 경우든 active 는 남는다. 나중에 `/yultopia:cc` 로 이어 할 수 있다고 알린다.

## 8. 대기와 진행 보고

- `call` 이 0 이면 그 한 줄(`[cc] Codex 호출 시작: …`)을 보여주고 대기 루프에 들어간다.
- **대기 루프**: `cc-codex.sh wait` 를 **반드시 포그라운드로, Bash 도구 `timeout: 600000`** 으로 부른다(`run_in_background` 를 쓰지 않는다). 기본 2분 제한으로 부르면 대기 명령이 끊기고, 끊기면 Codex도 중단된다.
  - exit 0 → 결과 JSON 한 줄 → 6장.
  - exit 2 → 진행 한 줄(`[cc] Codex 실행 중 · 호출 N · 경과 M분 · 마지막 활동 S초 전`)을 사용자에게 그대로 보여주고 다시 `wait`.
  - exit 3 → 7장.
  - exit 130 → 이 대기가 끊겨 Codex를 멈췄다. 그 줄을 전하고 사용자 말을 기다린다.
- 단계가 바뀔 때마다 한 줄: `[cc] Codex 계획: 마일스톤 3개 (…)`, `[cc 1/3] Claude 작업 중`, `[cc 1/3] Codex 검수 중`, `[cc 1/3] Codex 반려 (1/3): …`(반려 횟수는 `status` 의 "연속 반려"), `[cc 2/3] Codex 승인 → 다음: …`, `[cc 1/3] Codex 답변: …`(메시지 결과).
- Claude 자신의 구현이 길어지면 도구 호출 사이사이에 대략 10분마다 한 줄(경과 시간, 지금 하는 일). 사용자가 10분 넘게 소식을 못 듣는 일이 없게 한다.
- 호출 번호는 재시도 때문에 건너뛸 수 있다(오류 아님). `cc-codex.sh status` 는 단계·호출 수·연속 반려·토큰 한 줄이다. 1(상태를 읽을 수 없음)이면 잠시 뒤 한 번 더 부른다.

## 9. 중단 후와 훅 알림

- 사용자 메시지에 `[yultopia cc]` 로 시작하는 추가 정보가 붙으면, 기다리는 쪽 없이 Codex가 돌고 있다는 뜻이다.
  - "Codex가 실행 중입니다"(보통 고아): 사용자 말에 맞춘다. 멈추거나 방향을 바꾸려는 말이면 아래 "Codex 멈추기". 계속하라는 말이면 대기 루프로 `wait`. 애매하면 "돌고 있는 Codex를 멈출까요, 기다릴까요?" 묻는다.
  - "확인할 수 없는 프로세스가 프로세스 그룹 <pgid>": /cc 는 종료하지 않는다고 알리고 `ps -o pid,command -g <pgid>` 로 직접 확인할 수 있다고 전한다. 죽이지 않는다.
- `check-orphan` 종료 코드: 0 = 고아 없음 / 10 = 한 줄을 읽고 판단(종료함, 이미 끝남, KILL 뒤에도 남음, 확인 못 해 종료 안 함) / 1 = 오류.
- 사용자가 Esc 로 대기를 끊은 뒤 멈추거나 방향을 바꾸라고 하면: 대기 명령이 끊기면서 Codex도 멈추지만 확인하지 못해 남았을 수 있다. 사용자 말을 Codex에 전하기 전에 아래 "Codex 멈추기" 를 먼저 하고, 그다음 6장 "사용자 말 전달".
- 세션 시작 때 오래된 /cc 기록 정리 알림이 보이면 따로 할 일은 없다. 관련 있을 때만 언급한다.

**Codex 멈추기** (사용자가 멈추거나 방향을 바꾸라고 했을 때만. 사용자 말을 Codex에 전하기 전에 한다):
1. `cc-codex.sh check-orphan --kill` 을 실행한다. 사용자가 시킨 종료라 고아 유예 시간을 기다리지 않는다. 다른 대기 명령이 살아서 기다리는 호출은 멈추지 않는다.
2. 결과에 따라:
   - 10 이고 줄이 "종료했습니다" 또는 "이미 끝나 있었습니다" → 멈췄다. 원래 하려던 명령(`call`, `discard`, `finish`)을 한 번만 다시 한다.
   - 0(출력 없음) → 멈출 Codex가 없다. 원래 명령을 한 번만 다시 한다. 그래도 "이미 실행 중"·"Codex가 실행 중입니다" 면 다른 곳(다른 세션 등)의 대기 명령이 기다리는 중이라 멈추지 않았다고 쉽게 알리고 멈춘다.
   - 10 이고 줄이 "확인하지 못해"(안전하게 멈출 수 있는지 확인하지 못함), "KILL 뒤에도"(일부 남음), 또는 "프로세스 그룹 <pgid>"(확인할 수 없는 프로세스) → 그 뜻을 쉬운 말로 전하고(프로세스 그룹이 적혀 있으면 `ps -o pid,command -g <pgid>` 로 직접 확인할 수 있다고) 멈춘다. 다시 시도하지 않는다.
   - 1 → 그 줄을 전하고 멈춘다.

## 10. 이어 하기

1. `cc-codex.sh path brief` 로 정리본 위치를 얻어 Read 로 읽는다(읽기만). 이것이 대조 기준이다.
2. `git status --short` 로 바뀐 파일을 짧게 보여준다(이전 /cc 작업의 변경이므로 깨끗함 검사는 하지 않는다).
3. 대기 루프로 `cc-codex.sh wait` 를 부르면 단계(`phase`)별로 갈린다:
   - 0 → 마지막 Codex 결과(working·asking·done 단계). `git diff` 로 이미 한 일을 확인하고 이어서 한다. `approve`·`reject` 는 검수 결과인지 메시지 답변인지 모르므로 메시지 답변처럼 다룬다: 지금 마일스톤(preflight 의 `active.milestone`)을 `instruction` 대로 이어 가고 검수를 받는다. `ask_user` 면 질문을 다시 묻고, `done` 이면 11장, `plan` 이면 4장.
   - 2 → 아직 실행 중(planning·reviewing 단계). 계속 기다린다.
   - 3 이고 "기다릴 Codex 호출이 없습니다" → 계획 전: `call plan`.
   - 3 그 밖(failed·interrupted 단계) → 그 줄을 전하고 다시 부를지 묻는다. 다시 부르라면 마일스톤이 없으면 `call plan`, 있으면 현재 마일스톤 상태를 확인해 보고를 다시 저장하고 `call review`(사용자 메시지 전달 중이었으면 `call message`).

## 11. 완료

`done` 이 와도 바로 지우지 않는다.
1. `cc-codex.sh status` 로 Codex 토큰 사용량을 얻는다.
2. 결과를 짧게 보여준다: 마일스톤별 결과, 바뀐 파일(`git status --short`), 검증 결과, Codex가 남긴 지적(`findings`, 있으면), 토큰 사용량.
3. "완료로 할까요? 커밋할까요?" 묻는다.
   - 커밋하라면 그때만 커밋한다. 푸시는 하지 않는다.
   - 완료 → `cc-codex.sh finish`. 0 이면 끝. 6 이고 줄이 "Codex가 실행 중입니다" 면 사용자가 완료를 고른 것이므로 9장 "Codex 멈추기" 를 한 뒤 finish 를 한 번만 다시 한다. 6 의 그 밖의 줄이면 그 줄을 전한다(Codex가 돌 수 있음. 프로세스 그룹이 적혀 있으면 `ps -o pid,command -g <pgid>`). 1 이면 그 줄을 전한다.
   - 추가 수정 → 6장 "사용자 말 전달"(정리본 갱신 + `call message`)로 보내고, Codex 답변의 지시대로 추가 작업을 한 뒤 5장 3~5로 검수를 받는다. 이 추가 작업은 새 마일스톤이다: 번호는 결과의 `milestone`(지금 번호보다 크지 않으면 지금 번호 + 1)이고, 검수는 추가 수정을 요구한 때부터 바뀐 것만 본다.
