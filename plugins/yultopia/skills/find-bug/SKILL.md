# find-bug

코드는 수정하지 마라. 이 스킬은 특정 증상이나 로그를 기준으로 원인을 찾는 조사/보고 전용이다. 모든 응답은 한국어로 작성한다.

## 프로젝트 고유 규칙 읽기 (먼저 한다)

1. `AGENTS.md`, `CLAUDE.md`를 먼저 읽는다.
2. **`## Yultopia 중점 점검 항목`** 절이 있으면 그 도메인 위험·데이터 흐름·민감정보 목록을 조사 기준으로 삼는다.
3. 없으면 일반 기준으로 진행하고 되묻지 않는다.
4. 문서에 적힌 민감정보 필드는 출력 금지 대상으로 취급한다.

## 입력 해석

- 조사 단서(인자): `$ARGUMENTS`
- 사용자가 요청/응답 캡처, 로그, 시간, 오류 문구, 결과코드를 주면 그것을 재현 단서로 삼는다.
- "서버 로그 봐", "왜 이래", "어떤 문제야"라고 하면 로그/코드/DB 읽기 조사까지 진행한다.
- 인자가 파일이나 기능명이면 그 범위에서 원인을 찾는다.
- 특정 증상이 없고 "전체적으로 봐줘"에 가까우면 `yultopia:code-review` 성격이라고 판단하되, 사용자가 이 스킬을 썼으면 버그 위험 중심으로 좁혀 보고한다.

## 원칙

- 코드 수정 금지.
- 커밋/푸시 금지.
- DB 쓰기, 백필, 시드, 스키마 변경 금지.
- 로그, 코드, 설정, DB는 읽기만 한다.
- 개인정보, 인증정보, 토큰, 비밀번호, secret 값은 출력하지 않는다.
- 확실한 사실과 추정은 분리한다.
- 원인 확인 전에는 수정 방향을 단정하지 않는다.
- 증상만 보고 어느 컴포넌트 책임인지 섣불리 정하지 않는다.
- 실제 로그나 코드 근거가 없으면 `추정`이라고 표시한다.

## 조사 순서

1. 사용자가 준 증상과 시간, 입력값, 응답/결과코드를 정리한다.
2. `AGENTS.md`, `CLAUDE.md`와 문서가 가리키는 추가 문서를 읽는다.
3. 관련 로그를 찾는다.
4. 요청 진입 → 검증 → 처리 → 저장/외부호출 → 결과 반영 순으로 코드 흐름을 따라가며 어느 단계에서 문제가 생겼는지 좁힌다.
5. 필요하면 DB는 읽기 쿼리만 사용하고 민감값은 마스킹한다.
6. 재현 가능 조건을 정리한다.
7. 고치지 말고 보고만 한다.
8. 사용자가 "쉽게"라고 하지 않아도 마지막 결론은 쉬운 말로 다시 정리한다.

## 보고 형식

1. 결론: 어떤 문제인지
2. 위치: 어느 파일/함수/단계 문제인지
3. 원인: 왜 그런 일이 생겼는지
4. 증거: 로그/DB/코드에서 확인한 핵심 단서
5. 영향: 사용자가 겪는 현상
6. 수정 방향: 실제 수정은 하지 않고 방향만 제안

짧은 답이 필요하면 먼저 이렇게 말한다.

```text
결론: 어떤 영역에서 어떤 문제가 생겼는지.
위치: 파일/함수는 여기다.
원인: 쉽게 말하면 이렇다.
```

## 표현 방식

- 문제 영역과 유형을 먼저 말한다 (예: "입력 검증 문제", "저장 경로 문제", "결과 매핑 문제", "비동기 반영 문제", "쿼리/스키마 문제").
- 원인에 짧은 이름을 붙인다 (예: "검증 누락", "JSON 형식 오류", "중복/멱등성 부족", "매핑 누락", "비동기 레이스", "파라미터 바인딩 누락").
- 긴 기술 설명 전에 한 줄 요약을 먼저 준다.
- 사용자가 화가 난 상태라면 변명하지 말고 핵심부터 말한다.

## 금지

- "아마 그럴 것 같다"만으로 결론 내리지 않는다.
- 코드를 고치지 않는다.
- 운영 데이터 변경을 하지 않는다.
- 민감값 원문을 출력하지 않는다.
- 조사 도중 발견한 별도 버그를 고치지 않는다. 필요하면 별도 항목으로 보고만 한다.
